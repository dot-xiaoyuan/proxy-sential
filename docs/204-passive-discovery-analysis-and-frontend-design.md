# 204 被动发现现状分析与前端改进设计

## 一、被动发现管线现状——做到了多少

### 1. 信号采集层

镜像流量经 `packet-sidecar` 采集，通过 `stateChangeTracker` 变化检测后产生标准事件。已实现的信号源和处理程度：

| 信号源 | 采集状态 | 解析深度 | 分类贡献 | 现场效果 |
|---|---|---|---|---|
| **ARP** | 已量产 | MAC-IP 绑定 + VLAN | 地址发现（基础） | 现场日产 ~18.8M 事件（优化后），设备去重覆盖校园网主要网段 |
| **DHCP** | 已量产 | hostname、vendor_class、requested_options、client_id_hwtype、option93 | 操作系统推断(Android/Windows)、设备厂商线索、PXE 终端识别 | 有字段级证据引用，区分历史线索与当前租约 |
| **SSDP/UPnP** | 已量产 | NT/ST/USN/Server/Location + XML description 拉取(manufacturer/model) | 路由器(iKuai)、媒体设备、网关识别 + 厂商型号自报 | 现场大量播报（单 bucket 469 条 SSDP），已做变化抑制 |
| **LLDP/CDP** | 已量产 | system_capabilities、system_name/description | 交换机/AP/路由器能力位判定 | LLDP 邻居自报能力 → 设备类型直接结论 |
| **mDNS (DNS-SD)** | 已量产 | 服务类型 + 主机公告 + TXT 记录中型号键 | 打印/扫描/投屏/视频/语音能力 → 哑终端品类 | 服务公告能力线索已在前端展示 |
| **SADP** (海康私有) | 已量产 | probe_match 响应：product_model + L2 source 验证 | 海康摄像机/录像机精确型号 | 现场已匹配 DS-2CD/DS-7916 等型号 |
| **NBNS/LLMNR** | 已量产 | 名称解析 | 设备名称线索 | 补充 hostname 发现 |
| **NDP** (IPv6) | 已量产 | IPv6 邻居 | IPv6 地址绑定 | 覆盖双栈设备 |
| **IEEE 1905** | 已量产 | 客户端关联 | AP-终端拓扑关系 | 无线终端归属 |
| **HTTP UA** | 已采集 | User-Agent 字符串 | 操作系统+浏览器 → 设备类型弱线索 | 标记为"仅按当前 IP 关联，需核对地址归属" |
| **TLS (JA3/JA4)** | 已采集 | ClientHello 指纹 | 操作系统/应用弱线索 | 握手弱线索已展示 |
| **IPP** | 已实现 | 打印协议响应 | 打印设备精确识别 | 探测响应模式 |
| **ONVIF** | 已实现 | 视频设备协议 | 摄像机识别 | 探测响应模式 |
| **SNMP** | 模型已定义 | 社区字符串探测 | 网络设备识别 | 现场未大规模启用 |
| **BACnet/Modbus/CoAP/MQTT** | 模型已定义 | 工控/楼宇协议响应 | 工控/楼宇设备识别 | 被动观察未见流量，需主动探测 |
| **RTSP/SSH/SIP** | 模型已定义 | 协议响应 | 摄像/管理/语音设备 | 被动观察有限 |
| **WS-Discovery** | 模型已定义 | Web 服务发现 | 打印/扫描设备 | 被动可捕获 |
| **FDB/Neighbor** | 已量产 | 交换机 MAC 表 + ARP 表 | 基础设施拓扑 | 读取时间不代表终端观测时间 |

### 2. 设备分类与哑终端识别

**分类管线流程**：
```
镜像流量 → 协议解析 → 标准事件 → 变化抑制 → 观测入库
  → OUI 厂商查找 → 产品规则匹配 → 服务能力推断
  → 指纹库匹配 (fingerbank) → 硬件类型裁决 → 当前状态投影
```

**已实现的分类维度**：
1. **OUI 厂商识别**：MAC 前缀 → 厂商名 (Hikvision → 摄像设备 likely)
2. **产品规则匹配** (`product-rules.json`)：正则匹配型号字符串 → 精确设备类型。当前 12 条规则，覆盖海康(DS-2CD 摄像、DS-79/77/96 录像、DS-K1T 门禁)、大华(IPC/NVR)、Apple TV、Chromecast、ZKTeco
3. **协议能力推断**：LLDP 能力位(bit4=路由,bit3=AP,bit2=交换)、SSDP(InternetGatewayDevice→网关, MediaRenderer→媒体)、mDNS 服务类型(\_ipp→打印, \_airplay→投屏等)
4. **名称模式**：DHCP hostname/vendor_class(Android/vivo-→手机)、LLDP/SSDP 中 iKuai→路由器
5. **指纹库**：独立 fingerbank 模块，包含 DHCP 指纹、OUI 映射、应用层规则，支持分层裁决

**已识别的设备类型** (对应 `DiscoveryDeviceIcon`)：
printer, camera, access_point, router, switch, mobile, tablet, desktop, voip_phone, media_player, gateway, firewall, wireless_controller, recorder, access_control, attendance, pos_terminal, medical_device, industrial_controller, environmental_monitor, ups_pdu, smart_tv, digital_signage

**哑终端品类判定** (`dumbTerminal` 函数)：
- 排除网络基础设施(AP/路由/交换/网关/防火墙)
- 按能力映射：printing/scanning→打印/扫描, casting/media_rendering→媒体播放/投屏, network_video→视频监控, voice→语音话机
- 未命中任何品类 → 空（即"未明确品类的非网络设备"）

### 3. 现场实际效果（从代码和文档推断）

- **设备发现数量**：现场覆盖校园网多 VLAN 网段，日均发现数万设备（多传感器去重后）
- **类型覆盖率**：覆盖报表页有"设备类型识别率"指标，已确认类型 + 画像线索 + IP 产品线索三层
- **哑终端品类**：打印机、摄像机通过 mDNS/SADP/产品规则有较高识别率；门禁、考勤机依赖具体厂商产品规则
- **痛点**：大量设备停留在"ARP 地址候选"或"缺少类型证据"状态，只有 MAC-IP 绑定无法进一步分类

## 二、还可以做什么——提升哑终端识别的方向

### 方向 1：丰富产品规则库（投入小、见效快）

当前 `product-rules.json` 仅 12 条规则。校园网常见但尚未覆盖的哑终端品牌/型号：

| 品类 | 典型厂商 | 可匹配信号 | 预估覆盖增量 |
|---|---|---|---|
| 打印机 | HP/Canon/Epson/Brother/联想/奔图 | mDNS TXT md=/ty=、IPP printer-make-and-model、SNMP sysDescr | 高——校园打印机数量大 |
| 考勤/门禁 | 中控(ZKTeco)、海康(DS-K1T) | SADP/SSDP 型号自报 | 中——已有海康规则，可扩展中控系列 |
| IP 话机 | Yealink/Polycom/Grandstream/华为 | SIP UA、DHCP vendor_class(如 "Yealink SIP-T")、LLDP MED | 中 |
| 投影/显示 | 爱普生/明基/NEC | SSDP description | 低——需现场观察播报情况 |
| POS/收银 | 商米/新大陆 | 应用层流量特征 | 低——需专项分析 |

**行动**：从现场已采集的 SSDP/mDNS/SADP/DHCP 数据中导出未匹配型号自报，统计 Top-N 后编写产品规则。

### 方向 2：DHCP 指纹深化

DHCP 字段已在采集但分类利用有限：
- **vendor_class**：`MSFT 5.0`(Windows)、`android-dhcp-*`(Android)、`udhcpc`(嵌入式 Linux) 等标准模式
- **requested_options (parameter request list)**：不同操作系统和设备类型的选项列表组合有指纹特征，fingerbank 已有此能力
- **option 93 (Client System Architecture)**：PXE 终端标识，已采集 `dhcp_option93_present`
- **hostname 模式**：`HP*`/`EPSON*`/`NPI*`(打印)、`Android-*`/`Galaxy-*`(手机)、`iPhone`/`iPad`

**行动**：增强 `NormalizeObservationClassification` 中 DHCP 分支的模式匹配，特别是 vendor_class 到设备类型的映射表。

### 方向 3：TTL/TCP 栈指纹强化

已有 TTL 采集和证据引用，但分类利用可扩展：
- TTL=64 通常 Linux/Android/macOS, TTL=128 通常 Windows, TTL=255 通常网络设备
- TCP Window Size + TTL 组合可进一步区分操作系统
- 结合 OUI 和 TTL 可提高"某 MAC 是哑终端(Linux 嵌入式)"的置信度

### 方向 4：流量行为画像（中长期）

不依赖协议解析，通过流量模式识别设备类型：
- **DNS 查询域名模式**：`*.hikvision.com` → 海康设备、`*.canon.com` → 佳能打印机
- **目标端口分布**：只访问 TCP/554(RTSP) → 视频设备、TCP/9100(RAW printing) → 打印机
- **流量节律**：固定间隔小包 → IoT 传感器/心跳设备、只在工作日活跃 → 办公设备
- **NTP 服务器偏好**：嵌入式设备常有硬编码 NTP 服务器

现有 `observed-ports` 接口已按 IP 聚合近 2 小时目标端口，但尚未用于自动分类。

### 方向 5：主动探测补充

已有 `ScanConfig` 和 active origin 支持：
- **IPP 探测**：已实现，可定向扫描 ARP 发现的 IP 验证打印机
- **ONVIF 探测**：已实现，可定向扫描验证摄像机
- **SNMP 探测**：模型已定义，sysDescr/sysObjectID 是网络设备和打印机的权威标识
- **HTTP 探测**：许多哑终端有 Web 管理页面，Server header + 页面标题可识别

## 三、前端发现设备页面分析与改进设计

### 现状问题

从 `PassiveDiscoveryPanel.tsx` (~485 行)分析，当前页面存在以下问题：

**呈现问题**：
1. 纯表格视图，统计概览折叠在 `<details>` 标签里，不显眼
2. 类型分布、趋势等关键信息需要手动展开"类型与处理状态快捷筛选"/"采集与识别状态"才能看到
3. 设备详情是 Modal 弹窗，信息密度高但结构扁平——几十个字段一字排开的 `<dl>` 列表
4. 哑终端没有独立视角，"哑终端线索"按钮只是按能力过滤，无品类统计
5. 移动端表格列太多，虽然有 `scroll.x=1125` 但体验差

**筛选问题**：
1. 筛选器分散在三层：快捷按钮行 + 主筛选器 + "更多筛选"折叠面板
2. 类型筛选是多选下拉框，设备类型多时需要逐个找
3. 没有"按厂商"快捷筛选（虽然有搜索）
4. 时间范围选项少（15m/24h/7d/30d），缺少自定义范围
5. 组合筛选保存在 localStorage 但入口不明显

**统计问题**：
1. 总览条只有数字 + 按钮，没有可视化
2. 类型分布只有文字列表，没有图表
3. 趋势只有 5 格条形，分辨率太低
4. 缺少 VLAN/网段维度的设备分布统计
5. 缺少哑终端品类的独立统计面板
6. 识别质量数据加载后仍然不够直观（百分比+数字散列）

- 迷你趋势条复用现有 `trends` 接口数据
