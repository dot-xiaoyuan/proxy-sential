# 接口性能盘点与慢页面原因（2026-09-17）

当前测量确认了两类后端问题：运营模块把轻量元数据操作与全部案件证据历史绑定，且串行持锁；应用活动查询先对七天观测做全量版本去重，触发内存限制和查询超时。骨架屏是在等待这些接口，不能靠缩短前端加载动画解决。此次只增加诊断、基准测试和报告，没有修改运行时逻辑，也没有部署到 30。

## 测量范围与限制

- 从当前 OpenAPI 盘点 101 个操作：66 GET、34 POST、1 PUT。30 上全部 66 个 GET 各采样三次；业务写入只在一次性本地 PostgreSQL/ClickHouse 上测试。登录会创建独立测试会话，但不修改业务配置。
- 串行 HTTP 计时包含网络、后端处理和完整响应读取；生产环境仍有正常采集与后台任务。三次样本的 p95 就是最大值，只供定位，不能代表稳定 SLA 或最大吞吐能力。
- 本地全量接口初测是小数据集；随后使用 47 个案件、24,000 份合成快照（JSON 约 147MB）做集中复现和补测。没有复制生产数据。
- 2xx 的空列表只证明接口成功，不能代表生产规模的性能。400/401/404/409 等错误响应单独列出，不算成功业务基准。
- 最终合并清单：现场 52 个读取操作全部为 2xx，3 个应用活动操作全部 503，11 个读取操作因未启用功能或缺少匹配样本返回 404；隔离环境 64 个操作全部为 2xx，37 个操作只覆盖了错误或不可用路径。
- 缺少的正常业务样本包括 OIDC、政策执行审批、集成鉴权事件及重放、外部/原生处置连接器与回调、部分历史事件详情、离线包上传、应用库远程更新。必须补齐对应夹具、包和集成配置再压测，不能宣称这些正常路径已验证。

## 原因一：校区和工作台被案件证据历史拖慢

`operationsMutex.Lock()` 不仅加 Go 锁，还调用 `beginLocked()`；后者开启 15 秒后台上下文事务、取得全局 PostgreSQL advisory lock，再 `reloadPostgres()` 全量加载政策、校区、SLA、案件、连接器、处置及全局设置。`loadCases()` 会读取全部案件评论、时间线和证据快照并逐条 JSON 解码。

因此读取很小的校区配置、统计案件数量、保存一个校区，都必须支付全部运营数据重载成本。写入还会保存当前运营文档中的多个模块。Go 全局锁和数据库 advisory lock 把这些请求串行化，用户操作与后台任务会相互排队。

现场只读核对：47 个案件、1 个校区、23,993 份证据快照；快照存储内容约 64MB，解码后的 JSON 约 144MB。快照 SQL 的 EXPLAIN ANALYZE 约 94.6ms，并发生外部排序；该时间不包含完整 JSON 传输、Go 解码及锁等待，不能据此认为 HTTP 重载只需 95ms。数据库活动中也观测到全量快照读取。

隔离复现（各项为平均 HTTP 耗时）：

|请求|小历史，串行 10 次|24,000 快照，串行 5 次|24,000 快照，4 并发共 8 次|
|---|---:|---:|---:|
|`GET /organization`|9.6ms|763.7ms|2470.2ms|
|`GET /overview?window=24h`|37.7ms|703.1ms|2516.5ms|
|`POST /organization/campuses`|15.7ms|766.9ms|2503.7ms|

这里的校区保存始终写同一个合成校区。大历史导致串行保存约 767ms，四并发平均约 2.5 秒，符合全局锁排队现象；这些是本地复现值，不是 30 上实际保存耗时。为避免变更现场配置，没有在 30 上重新提交校区。

Go benchmark 同一大历史数据库、各三次：组织表单独读取约 1.269ms、5.2KB 分配、134 次分配；全量运营重载约 748.691ms、363,542,352 字节分配（约 347MiB）、531,011 次分配。时间相差约 590 倍。这里的字节是每次调用累计分配量，不是常驻或峰值内存。

案件列表走独立分页数据库查询，现场约 8–10ms，证明相同数据库上小范围查询可以很快。案件详情仍走全量重载，现场中位数约 10 秒。

工作台 `/overview` 还串行执行传统统计、ClickHouse 活动统计和 `operationsSummary()`；最后的案件统计又进入上述全量加载。证据类型统计的现场 EXPLAIN ANALYZE 约 297.6ms，涉及约 170 万行的并行全表扫描，应优化，但不能单独解释全部 15 秒。

代码还存在一个待修复的错误传播问题：锁初始化失败保存在 `lockErr`，部分读取处理器未检查便读取旧文档。不能只按 HTTP 200 判断读取一定新鲜。本次未证明某一具体校区响应发生了陈旧读取。

## 原因二：应用活动七天去重超过查询预算

`appLatest()` 总是先扫描 `now()-7 DAY` 到查询截止时间的观测，以 `(sensor_id,event_id)` 和分类版本做 `argMax` 去重；`appActive()` 才筛选用户指定的窗口、IP、校区。选择 1h 或 24h 并不等于前置去重只处理对应窗口。报表还执行多条独立聚合。

现场 `application_observations` 活跃数据部分约 10,098,233 行、压缩磁盘约 875MiB。源码每条查询限 2 线程、512MiB 内存、20 秒；ClickHouse `system.errors` 只读核对发现：

- `MEMORY_LIMIT_EXCEEDED`：请求约 515.23MiB，超过 512MiB。
- `TIMEOUT_EXCEEDED`：约 20,007ms，超过 20,000ms。

三类应用活动接口各三次全部返回 503，耗时约 13.6–20.1 秒。这里记录的是失败耗时，不能看成业务完成耗时。现场查询日志未返回可用记录，因此没有给每次 HTTP 失败伪造独立的数据库 query_id。

## 其他观察

设备信号列表单次响应约 1.17MB。大响应会增加传输和浏览器解析成本，但本次没有测浏览器渲染时间，不能把它直接认定为骨架屏主因。

## 建议修复顺序

1. 校区/楼栋/网络区域/接入点改为独立范围读取和写入，不进入案件历史重载。工作台案件总数用聚合 SQL；案件详情只加载该案件，历史分页。
2. 去掉轻量读取的全局写事务及全量重载，限定真正写操作的事务与冲突范围；遵循请求上下文，明确返回锁/数据库失败。
3. 应用活动采用预计算的最新事件版本/聚合或适当索引与范围下推，避免每页重复七天全量去重。必须保留分类版本决胜及连接累计字节语义，不能简单缩短窗口而改变统计含义。提高内存/超时不是根本修复。
4. 给工作台统计做有界聚合与短周期缓存，限制大列表默认返回量；优化后按同样数据规模回归，补齐外部集成正常样本，再进行持续负载和吞吐测试。
