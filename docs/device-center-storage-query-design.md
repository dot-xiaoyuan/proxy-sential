# 设备中心存储与查询设计

设计日期：2026-10-13。状态：第一阶段已落地到工作区，现场迁移、历史回填与容量验收待后续发布任务完成。

强制约束见 [AGENTS.md](../AGENTS.md#存储查询与容量约束)，总体分工见 [生产数据架构](production-data-architecture.md)。本文记录目标设计和当前实现边界，不能作为现场容量已达标的证明。

### 现阶段已实现的边界

- 设备列表已使用绑定筛选条件和末行键的不透明游标；旧数字 `cursor` 会明确返回迁移错误，统计请求不携带列表游标。
- 列表请求不再使用固定 TTL 结果缓存；相同请求仍可在并发窗口内合并，投影结果变化不会被五秒缓存遮蔽。统计仍由独立接口缓存并附时间。
- PostgreSQL 迁移 `110_device_inventory_incremental_deltas.sql` 增加紧凑变更账本。投影首次回填允许读取历史；完成后新增事件只应用受影响的关系和检索行。
- 更正、撤销和删除会进入修复状态，保留未完成任务并标记 `projection_repair_required`，不会把旧投影报告成已追平。
- 发现记录列表已从请求内历史聚合切换为 `discovery_observation_latest` 候选读取；使用绑定筛选条件的游标，旧 `offset` 和不匹配游标返回明确错误。
- 发现搜索先在 IP、MAC、名称、厂商、型号等结构化 JSON 字段上做有界候选筛选；少于三个字符走前缀，三个及以上字符走包含匹配，并通过专用索引控制扫描范围。
- 投影工作线程按会话结束时间增量唤醒自然过期设备，并保存每设备过期检查水位，避免没有新事件时继续展示过期的当前关系或重复排队。
- 列表状态新增处理状态、接收/处理水位、最老待处理时间、处理延迟和结果版本字段；这些字段来自投影任务缺口，不能用最近成功记录替代。

迁移文件尚未在现场执行，回填、影子比较、10 倍组合负载和 24 小时验收仍是后续发布门槛。

## 1. 目标、范围和现状

目标为现场基线的 **10 倍设备数、历史量和持续写入速率，20 路并发查询**。继续使用 PostgreSQL 与 ClickHouse，不新增消息队列；允许按压测调整现有数据库配额，不承诺现有 PostgreSQL 3 GiB、ClickHouse 12 GiB 配额足以达标。

设备中心相关标准事件首次成功入库后，**5 秒内必须能由查询接口反映其处理结果**。这一要求约束数据新鲜度，与当前状态接口 P95 ≤500 毫秒、P99 ≤1 秒的响应目标分别验收。源系统尚未上报的等待时间不计入该 5 秒，但应另行观测。独立统计和归档任务报告处理进度及统计时间，不冒充实时结果。

### 1.1 审查基线

2026-10-13 对 184 的只读审查以现场 `2026.10.13-qianhu-1551`、源码 `7cae741f05dfc94a1079b20cfd6d12345b16bc55` 为版本基线。规模取数据库统计近似值，并非精确盘点：

| 数据 | 现场近似规模 | 10 倍审查规模 |
|---|---:|---:|
| 设备实体 | 7.36 万 | 73.6 万 |
| IP/MAC 历史 | 1,178 万条 | 1.18 亿条 |
| ClickHouse 标准事件 | 1.16 亿条 | 11.6 亿条 |

写入速率、峰值及热点分布须在压测前重新采样并随结果保存；不能由累计行数推算。设备相关归档一年可能比现有保留策略占用更多空间，容量预算必须单独计算，不能只把当前磁盘占用乘十。

审查发现以下增长风险：

- 发现列表在请求中读取窗口内历史、去重、关联、在 Go 中聚合后再分页；完整 SQL 在 30 秒保护上限内未完成。
- 地址筛选在请求中重建全网有效地址，计数、筛选项和列表可重复执行该计算；深 `OFFSET` 也没有限定扫描量。
- 现场发现缓存为 60 秒、终端统计缓存为 30 秒；发现缓存持锁加载。即使 SQL 加速，现有时效与并发设计仍不满足目标。
- 本地未发布的 inventory 投影把历史移出列表，但常规更新会删除重建该设备在多张结果表中的记录，并重新读取全部关联历史；不能直接作为长期方案部署。
- 事件发生时间游标、固定等待和跳过积压的调试策略存在漏处理及延迟风险；不能用最近一次任务成功来表示全部事件已追平。

## 2. 存储分层与事实语义

### 2.1 数据职责

以下是逻辑模型，不是本次新增的物理表或迁移。后续实现应沿用可用账本和身份标识，以新增版本化结果表替换不符合约束的读取路径。

| 数据层 | 存储与组织方式 | 职责与生命周期 |
|---|---|---|
| 入库批次账本 | PostgreSQL，小型批次记录及持久任务 | 批次校验、首次入库确认、消费缺口、失败与恢复依据 |
| 当前设备状态 | PostgreSQL，每个作用域内设备一行 | 名称、分类、置信度、冲突、最近观测、地址状态、结果及规则版本 |
| 当前关系及服务证据 | PostgreSQL，按设备、来源和业务键保存 | 地址绑定、认证会话、服务公告、有效期、撤销状态与证据引用 |
| 列表检索索引 | PostgreSQL，结构化字段与专用索引 | IP/MAC/账号精确检索、名称检索、常用筛选与排序 |
| 热查历史 | PostgreSQL，按入库时间分区的紧凑变更与关联记录 | 最近 30 天身份、地址、分类及证据变化追溯 |
| 历史归档 | ClickHouse，按时间分区并按检索路径组织 | 入库后一年内设备相关历史及必要支撑事件 |
| 案件证据 | 独立受保护记录与证据副本 | 不随普通历史到期失效，保留解释和审计依据 |

常用筛选、排序、关联字段使用结构化列；JSON 用于扩展信息和证据，不能成为常用查询的唯一入口。列表和状态行只保存有限摘要与证据引用，原始大文档只在证据展开时读取。

设备身份延续现有作用域与归属规则。不同传感器、网络域、VLAN 中的同 IP 不自动合并；MAC 随机化、IP 复用和归属冲突保留证据及置信度。发现服务只能形成具有来源的线索，不能直接变成确定身份、风险结论或处罚依据。

### 2.2 地址、观测与服务

- **当前有效地址**由尚有效的绑定或会话支持，包含来源、确认时间和有效期；必须响应释放、换绑、撤销及自然过期。
- **最后观测地址**表示最近一次实际观测，不表示当前有效或在线。
- **历史地址**保留实际观测点或来源明确的会话区间；不把首次与末次观测之间的空档推定为持续占用。
- 服务证据保留作用域、来源、协议、服务实例、地址、端口、撤销状态和有效期。先核对历史去重与 current/latest 的键语义，再迁移，不能因换表而丢掉地址变化。
- 同时间的矛盾证据保留候选和冲突，不任意选择一条包装成确定结果。未来时间事件可追溯，在其生效前不改写当前状态。
- 哑终端分类延续服务证据要求及手机、电脑、网络设备的排除规则；性能优化不得降低证据门槛来填充列表。

### 2.3 保留、归档与清理

热历史以首次入库时间保留 30 天，同时保存事件发生时间，使晚到事件仍进入热查范围。归档保留至首次入库后一年，而不是热查 30 天后再追加一年；重试和重放不延长原记录的保留起点。

一年范围针对设备身份、地址变化、发现证据及必要标准事件，不自动把所有流量明细延长至一年。当前状态独立于历史分区，不能随历史清理而消失。

归档必须先完成批次数量、标识与校验核对，再允许删除热副本。案件引用证据在普通数据到期前获得受保护副本，清理遵守案件与审计规则。归档失败保留原数据、标记积压并报告容量风险，不能删除唯一副本。

分区清理和非分区补偿清理都需可中断、可恢复并限制 I/O；测量清理能力是否持续大于过期数据产生速度。索引、事件幂等记录、任务账本、缓存和过渡版本也要有对应保留及失效规则，不能留下无界增长的辅助表。

## 3. 可靠入库与增量处理

### 3.1 批次协议

扩展已有 `ingest_batches`、`ingest_checkpoints` 的职责及统一批次接口，不建立互不关联的第二套确认进度。认证接口、文件采集和发现采集使用一致的确认与恢复协议。

```text
标准事件
  → 登记持久批次与重试依据
  → 写入 ClickHouse，确认批次完整性
  → 同事务提交 PostgreSQL 批次状态及待处理任务
  → 增量更新设备状态、检索关系和热历史
  → 同事务提交处理进度与结果版本
  → 查询接口读取新版本
```

采集热路径通过现有缓冲／持久暂存交给入库工作线程，不执行复杂聚合或策略动作。批次携带稳定 ID、记录序号、数量、校验值及恢复引用；原始输入或持久暂存保留至批次可恢复且确认完成。

| 中断位置 | 恢复行为 |
|---|---|
| 批次已登记，ClickHouse 未确认 | 按稳定批次重试，核对完整性；不推进源检查点 |
| ClickHouse 成功，PostgreSQL 未确认 | 恢复任务核对已落库批次，补交确认和待处理任务；不遗漏、不重复计数 |
| PostgreSQL 任务已提交，处理未开始 | 持久任务保持待处理，工作线程重新领取 |
| 结果事务中途失败 | 回滚结果与进度，重试同一批次／子批次 |
| 结果提交后进程退出 | 从已提交进度恢复，幂等判断避免重复累计 |

源检查点只能在持久确认满足后推进。消费按任务状态保留缺口，不以最大序号或最大事件时间替代全部完成；较晚提交的低序号批次仍须可领取。通知只用于唤醒，持久任务才是工作依据。

事件按作用域、来源、事件 ID 和修订版本幂等处理；不能依赖 ClickHouse 后台合并保证即时去重。同 ID、同修订但不同内容记录为冲突，不静默覆盖。幂等及修订依据的保留必须覆盖可重放窗口；归档重放不得因热幂等记录已清理而再次增加计数。

### 3.2 增量应用

- 每批按设备合并变化，仅更新受影响关系和状态。重复上报更新确认时间、有效期与经幂等校验的必要计数，不重写不变画像。
- 使用事件发生时间和来源语义判断业务先后，使用入库确认和持久任务推进消费。晚到旧事件进入历史，不能覆盖更新的当前事实。
- 更正和撤销重算受影响关系及候选事实集；常规处理禁止查询该设备全部历史后重建。完整历史重建进入独立校验或修复任务。
- 大型认证快照分批解析、比较和应用，保存分块及比较进度；不反复反序列化整个 JSON，不使用覆盖整个快照的长事务。只有完整快照确认且差异计算完成后，才应用“缺失会话结束”的语义，不能把暂未处理的分块当作会话消失。
- 按到期索引处理租约、公告、会话和未来生效事实。没有新事件时仍更新当前状态、分类计数和缓存版本。
- 结果、热历史、消费进度及结果版本在同一 PostgreSQL 事务中提交，任务租约与版本校验防止过期工作线程覆盖新结果。
- 实时任务、回填、规则重算、修复、统计分开限流和连接配额；实时任务优先，后台积压不能挤占其全部资源。
- 规则升级在新版本中构建、验证并追赶实时变化，完成后切换；现行规则继续处理实时事件，不能暂停服务等待全量重算。

### 3.3 5 秒计时与处理状态

`T0` 为标准事件首次被存储成功确认的时点，`Tvisible` 为携带已提交结果版本的查询接口首次反映该事件处理结果的时点。以 `Tvisible - T0` 验收；不能从任务领取时开始计时，也不能把结果事务完成当作接口已可见。

保留事件发生时间、首次入库确认时间和结果应用时间。跨库中断导致首次确认时点暂时无法确定时，以持久记录的较早入库尝试时间保守计时并标记不确定性，不能使用恢复时间重置计时。批次整体确认时使用共享确认点，不等待批次全部处理结束才开始记录逐条延迟。

| 阶段 | 预算 |
|---|---:|
| 入库确认至批次可领取 | 0.5 秒 |
| 排队 | 0.5 秒 |
| 增量处理 | 2 秒 |
| 结果发布、缓存失效与查询可见 | 2 秒 |
| 合计 | 5 秒 |

移除固定等待 5 秒和超期跳过任务的设计。处理失败保留任务、重试并报告超限；隔离不可处理记录时保留缺口，不能将它记为成功处理。

“处理中”字段不等于已完成事件处理，不能据此让验收通过。无效或不适用事件需要确定的处理结果及原因；需要补充证据的分类可以保留不确定性，但已经具备的事实必须及时可查询。自然过期另以到期时间为起点验收及时性。

## 4. 查询、统计与接口契约

### 4.1 列表与检索

终端、网络设备、哑终端和发现线索读取各自状态投影及结构化检索关系。数据库完成筛选、排序和一页读取后，仅按该页设备 ID 补充有限摘要；不能全量取回 Go 再筛选或分页。

- IP、MAC、账号走精确索引；MAC 规范化，账号沿用既定大小写语义，不擅自折叠。当前 IP 检索与历史 IP 匹配分别返回来源。
- 名称及综合文本使用专用检索字段。按 Unicode 字符数判断：短于三个字符按前缀查询，三个及以上字符支持包含检索；界面明确方式，SQL 转义查询文本中的通配符，不修改用户输入语义。
- 常见作用域、分类、地址状态和最近观测排序采用适配查询的结构化索引。每个新增索引必须给出计划、扫描量和写入成本证据，不无差别构建所有筛选组合。
- 保留当前查询及历史匹配能力，不把历史地址命中展示为当前地址。超过 30 天的跨设备追溯进入独立归档查询任务，不能隐藏查询范围缩减或拖住当前列表。

采用不透明游标，绑定筛选条件、排序字段、末行键和查询版本；排序包含唯一设备键打破并列。移除深 `OFFSET`、任意跳页和第一页强制精确计数。无效、过期或不匹配游标返回明确错误，不退回无界查询。

实时翻页允许设备变化，不承诺多个请求组成同一个历史快照；页面刷新收敛变化。需要完整固定结果的导出使用独立快照任务，在固定查询水位上生成结果。

### 4.2 详情、统计与归档

- 详情首包仅返回当前摘要；关联、历史和原始证据各自限定设备／标识、时间范围和页大小，独立分页。
- 常用分类数量增量维护；不能对所有任意筛选组合预建计数。复杂组合精确总数进入独立统计任务，附统计版本及时间，列表不等待。
- 归档任务和统计任务独立限流，查询范围、进度、失败和结果有效期清晰可见；缺少归档或历史超出保留期不能伪装为无设备。
- 不以首尾观测补齐不存在的历史，不因冷热分层丢失冲突、撤销、来源或事件引用。

### 4.3 接口与缓存

以下是后续接口必须表达的逻辑契约，不代表本轮已修改 OpenAPI：

| 响应 | 必须表达的信息 |
|---|---|
| 列表 | `items`、`next_cursor`、`has_more`、新鲜度；不强制精确总数 |
| 新鲜度 | 入库水位、处理水位、最老待处理时间、延迟、结果版本、处理状态 |
| 匹配说明 | 当前或历史匹配、匹配字段、来源、观测／会话时间 |
| 统计结果 | 任务状态、总数或分类计数、统计时间、统计版本 |
| 历史与证据 | 独立游标、来源引用、保留范围、证据是否仍可获取 |

新鲜度按相关作用域的未完成缺口计算；不能用全局最大时间戳或最近一次处理成功表示追平。空队列、未准备、处理中、超限、失败和旧缓存状态必须可区分。查询失败不能返回成功的空列表或零计数。

缓存按结果版本失效，不允许长期 TTL 遮蔽已提交变化；新版本可见性纳入 5 秒总预算。取消跨查询键持锁加载，同键请求可以合并但必须支持取消。旧结果兜底附明确过期状态，不参与 5 秒达标计算；统计缓存用独立统计时间说明有效范围。

后续实现同步更新 OpenAPI、后端、前端与 mock。旧分页参数返回显式迁移错误，不回退全量扫描；前端旧链接保留筛选含义并重置到首屏。统计与归档任务展示进度；空值显示、证据层级和移动布局继续遵守 AGENTS.md。

## 5. 验证、容量判定与切换

### 5.1 回放与故障测试

先编写测试再实现替换，至少覆盖以下矩阵：

| 类别 | 场景与验收 |
|---|---|
| 幂等与时序 | 重复、跨批重试、乱序、晚到、未来时间、同时间冲突；计数及当前事实正确 |
| 身份与地址 | IP 复用、多地址、作用域隔离、租约释放／过期；不错误合并或推定占用 |

| 修订与审计 | 更正、撤销、案件引用、冷热边界；旧事实不覆盖新事实、证据可追溯 |
| 双库恢复 | 在每个入库与结果提交边界中断；任务不丢、结果不重复、不跳过缺口 |
| 并发与租约 | 工作线程崩溃、租约丢失、重启、回填及规则重算；旧线程不覆盖新结果 |
| 查询契约 | 冷热缓存、筛选游标不匹配、深翻页、历史匹配、独立统计；失败不伪装空结果 |

### 5.2 增长与稳定性测试

只在隔离环境造数和压测，保存可复现的生成种子与回放负载。分别构造 1 倍、3 倍、10 倍设备数、历史量及持续写入速率，再进行组合测试。数据需包含热点设备、长历史、重复上报、低选择性搜索、晚到与过期记录，不能只做均匀分布。

10 倍组合负载持续 24 小时并保持 20 路查询，穿插冷缓存、服务重启、规则重算和归档清理。每条相关测试事件记录首次入库确认到 API 可见的延迟，任何超过 5 秒的事件都计为违约；正常负载验收不得以分位数掩盖超限。故障注入也保留真实违约数，并分别报告恢复时间、缺口补齐和无数据丢失情况，不从报告中删除失败时段。

同时记录：

- API P95/P99、最大延迟、错误数、扫描行数、执行计划和结果大小。
- 队列最老年龄、实时／回填吞吐、任务重试、积压增长与恢复速度。
- 每批及每次设备变化的写入量、WAL、磁盘 I/O、内存、临时文件和索引维护成本。
- 热历史、归档、索引、账本、幂等记录、临时构建版本的增长量及清理速度。

增长验收关注工作量边界：固定设备及当前状态、只增加历史量时，当前列表不得转为扫描全部历史；普通增量更新不得按该设备全部历史长度重做。历史查询允许成本随明确选定范围增长，但必须分页、有任务预算和可取消性。

报告附硬件、容器配额、数据库配置、数据分布、入库速率、并发组合和原始结果。资源不足时说明吞吐、时效或归档容量缺口，不缩短保留、不跳任务、不宣称达标。不能把现场约 11.6 亿条事件的 10 倍规模外推为无需扩容即可保留一年。

### 5.3 后续实现与迁移次序

1. 建立回放、故障注入和基线测量，记录现有语义及差异；核对实际版本、迁移账本和工作区，区分已有改动。
2. 新增可并行验证的结果表与账本扩展；既有已应用迁移不改写，本地未发布投影不直接部署。
3. 先接收实时变化，再分批回填；用幂等与版本校验防止旧回填覆盖新事件，保持未完成覆盖范围可见。
4. 影子比较当前地址、设备分类、置信度、冲突、历史匹配及结果新鲜度，解释差异后完成增长测试。
5. 新旧读取路径通过开关切换并保留回退入口；数据库迁移向前兼容，应用回退不等于撤销数据迁移。
6. 归档核验、依赖检查和容量验收完成后，独立退役旧索引、旧表和过渡任务。旧流、重复归档或物化视图不能仅因名称相似而删除。

现场发布仍需单独授权，并遵守 AGENTS.md 的目标核对、迁移校验、测试联调规则和部署验收。本设计完成不代表实现完成或容量验收通过。

## 2026-10-13 增量处理修订与验证边界

数据库回放暴露的两个阻断问题已修订：普通 UPDATE/DELETE 不再一律进入无人处理的修复状态；单设备每批最多处理 500 条通知，结果与这批通知在同一事务提交，剩余通知保留待处理状态。按通知 ID 精确确认，不以最大 ID 推断较小 ID 均已完成。工作期间不持有来源通知行锁，提交时核对任务代次、租约所有者和有效期；不匹配则回滚结果和确认，后续重试。

新增迁移 `111_inventory_contribution_updates.sql`，不改写 103、110 的校验值。变更通知保留旧值与新值，设备归属变化会通知两侧设备。按来源和业务事件重读该事件的候选事实，按认证业务会话重读相关会话，替换该事件对账号、IP、接入位置关系的贡献。同一事件跨 IP/接入记录的重复贡献合并；关系计数使用新旧贡献差值，最早、最近观测与最高置信度由有序索引取首项。更正和撤销可回落到仍有效的候选，不需要重建设备全部历史。初始回填仍单独建立完整结果，不能以增量测试通过宣称初始回填已验收。

自然时间变化通过持久定时任务重新处理受影响事件或会话，没有新事件也能唤醒。认证快照中的消失确认不当成新的在线观测。最老待处理时间独立保存，后续写入、批次处理及重试均不得重置尚未完成的积压起点。

| 新增存储或索引 | 读取收益 | 写入成本 | 保留与失效 |
| --- | --- | --- | --- |
| `endpoint_inventory_contributions` 及关系时间、置信度、IP 索引 | 用事件定位、关系有序首项替代历史全量聚合；支持更正撤销和幂等 | 每事件通常产生账号、IP、接入位置三个以内的贡献；认证多地址会话按实际关系数增加；每次变化维护主键及 4 个查询索引 | 与事实版本关联，修订替换、撤销移除；设备删除时移除。正式归档必须区分历史搬迁与业务撤销，保留当前关系依赖的候选及案件证据，不能直接用源表 DELETE 充当归档。归档联动未完成，禁止直接启用这套表的历史清理 |
| `endpoint_inventory_projection_timers`、到期索引 | 按到期时间领取有限事件，避免每轮扫描全部会话 | 每个未来生效事件或会话至多一条下一次唤醒记录 | 处理时替换下一时点；无后续时点或设备删除时移除 |
| 快照事件、认证会话定位索引 | 只取受影响业务键 | 来源记录变更时维护额外 B-tree | 随来源记录生命周期；归档和退役仍需独立核验 |
| 关系最近时间索引 | 当前摘要只读取各类最近观测的并列候选 | 关系最近时间改变时维护 | 随关系记录生命周期 |
| 任务 `pending_since` 与索引 | 保留未完成缺口的年龄 | 每轮积压开始/结束维护一次，后续写入不重置起点 | 全部待处理通知与已到期任务完成后清空 |

本轮在 Apple M1、16 GiB 宿主机、Docker 8 vCPU/约 7.8 GiB 内存上的隔离 PostgreSQL 18 验证。历史增长用例为单设备同一账号/IP 的 1,000、3,000、10,000 个事件，各执行 20 次已有事件更正；最终回放日志中更新到投影事务完成的 P95 分别为 12.59、11.29、11.64 毫秒，最大值分别为 13.48、11.75、14.16 毫秒。测量包括来源更新和同步处理，不含生产排队、ClickHouse 入库或 HTTP API 可见时间，也未模拟 20 路并发。这只能说明该局部更新路径未随本组历史量线性增长，不能替代现场基线 10 倍组合负载、24 小时持续运行和逐事件 5 秒可见验收。

真实数据库回放覆盖：601 条通知分批、更正置信度、IP 更正、删除、账号冲突、跨表重复、归属迁移、事务回滚、租约丢失、并发来源写入、定时生效、显式认证会话更正与撤销、快照消失与撤销、初始快照分页。现场统计估算约 7.4 万设备和 1,182 万 IP 历史，该阶段本地验证时尚未在现场切换读取，也未造数；后续现场联调和实际发布情况见下文及现场评估记录。归档联动验证与完整容量验收仍未完成。

### 2026-10-13 现场联调范围与新增验证

本轮用户明确要求直接在 184 以现有数据部署和评估，暂不等待本地或隔离环境的 10 倍、20 路并发、24 小时容量验收。不在现场造数；该决定仅调整本轮发布验收范围，不构成 10 倍容量达标结论，也不取消长期容量约束。

设备投影现拆为独立 `inventory` 实时服务和 `inventory-backfill` 回填服务。回填负责初次设备登记、按设备初始化和认证快照，实时服务只处理已准备设备的增量与到期任务。现场发现队首长历史设备和认证事务锁竞争后，回填进一步将快照解析与设备初始化分别调度，设备初始化固定 4 个工作线程、数据库连接上限 12、CPU 上限 2 核、内存上限 1 GiB；实时服务连接上限 4、CPU 上限 1 核、内存上限 512 MiB。失败任务保留、可观测并重试；领取优先让其他可处理任务推进。迁移 114 的领取索引减少待处理队列排序，代价是每次任务状态变化维护一个额外部分 B-tree；仅覆盖未完成任务，完成后退出索引，无缓存失效或历史保留语义。

认证快照先流式解析为持久的 2,000 条片段，再以每事务最多 100 条的子批次应用；解析片段与应用进度分开，重启可从片段内部继续。全部片段完成后清除临时副本，原始快照仍是重试依据。该机制尚不能代替最终一年归档及受保护案件证据的完整生命周期实现。

现场影子校验命令 `inventory-audit --limit N` 对已追平设备使用一致性事务重算参考结果，比较后回滚，输出设备哈希与差异字段。命令不发布参考结果。小样本无差异只能证明样本一致性，不能代表容量或全部设备已就绪。

迁移 115 为 IP 与接入历史增加按设备、观测时间组织的覆盖索引，仅 INCLUDE 投影必需的标量字段（首次/最后观测、地址或接入点、账号、来源、事件 ID、置信度），不复制原始大文档。读取收益是初始回填及按设备历史读取可使用 Index Only Scan，减少长历史设备的随机回表；写入成本是每条相关历史插入/更正再维护一棵 B-tree，空间随来源历史增长，随来源记录生命周期回收，无单独缓存失效机制。本地历史增长回放与现场执行计划、索引实际空间须分别记录；不得把本地热缓存结果外推为现场容量。旧覆盖索引的合并退役留待依赖验证，不在本次迁移中删除。

初始投影与实时增量采用不同的发布校验：初次回填开始前捕获最多 500 个明确可见的通知 ID，在持有设备租约时生成贡献事实，并从该贡献集合统一重算初始关联计数、极值、地址点和摘要。发布只确认捕获的通知 ID；计算期间新提交的通知与序号缺口保持待处理。初始结果已完成后，即使旧代次尚未消费完，也转入增量处理，不因 `processed_generation=0` 再次扫描历史。该调整防止持续活跃设备不断废弃初始化结果；新变化仍必须继续处理，不能将初始化发布当成全部追平。常规增量仍保留代次和租约校验。新增并发回放验证“初始化期间新事件入库，初始化不丢弃、新事件保持 pending、随后补齐且计数不重复”。

### 分阶段提供当前摘要，不隐藏历史回填

现场联调中发现把首屏可用性绑定所有历史快照完成会使列表长期不可用。迁移 116 因此增加独立的摘要引导游标与完成标记：后台每批最多 2,000 个设备，仅复制已有识别摘要、设备基本字段和人工名称到检索结果表，绝不在请求内读取原始历史。已有完整投影通过 `ON CONFLICT DO NOTHING` 优先保留，摘要引导不确认任何待处理事件。所有设备的已有摘要准备后，接口 `available=true` 允许分页读取；`complete` 仍为 false，直到历史贡献和快照回填完成。前端明确显示“历史关联正在回填”，并说明历史检索与关联统计尚不完整。失败状态、最老待处理时间继续保留；此模式不计为满足 5 秒可见性。

这是一条受控上线过渡路径，不是用旧结果伪装追平：IP 历史匹配仍要求真实地址观测/会话证据，不能为了摘要阶段命中率而把旧摘要 IP 直接当成当前时间的地址事实。当前摘要引导只新增游标字段，复用已有索引表；写入成本为每设备首次一条摘要及有限账号键，后续由正常投影覆盖。没有额外持久缓存；当前状态保留规则不变。

### 184 发布兼容与真实规模评估（query16 / query17）

本轮部署前发现，现场 `identity-ui2` 已包含独立发现进程、采集 CIDR 限制和认证可靠收件箱；仅按当前旧分支构建会缺少现场参数及对应协议。候选现集成已部署分支的可靠批次回执、原始事件导出和恢复逻辑，并核对 104–109 等现场迁移，不修改已应用文件。未引入其过期积压跳过策略；身份派生恢复仍保留未完成位置，并在 SQL LIMIT 前保留事件 ID 边界，防止同一入库时间的大批事件反复读取第一页。应用更新脚本在切换前比较全部活动服务参数与候选帮助输出，参数缺失时提前失败。

query16 已在现场切换，使用已有数据完成 20 路并发、100 次混合查询，均返回 200。终端、哑终端、基础设施、网络设备在该短测中的 P95 分别约 281、130、70、73 毫秒；首次哑终端列表仍出现 6.87 秒长尾，不能视作完整查询性能达标。历史摘要与关联仍未全部追平，不满足逐事件 5 秒可见性，不能以热请求结果掩盖该缺口。完整数据与后续 query17 评估见 `artifacts/device-center-query-20261013/deployment-readiness.md`。

query17 将快照应用由每事务 2,000 条改为 100 条。读取仍复用原有持久解析片段，不重复解析整份 JSON，不丢弃历史，不手工推进完成标记。真实 PostgreSQL 回放验证片段内部重启、超过片段边界、重复回放以及缺失快照不制造在线区间。该改动减少通知行锁持有范围，增加事务提交次数；需用现场快照进度和 WAL/I/O 继续评估代价。

query17 现场复测发现，缩小事务仍不能消除认证快照与回填同时更新通知行的锁序冲突。query18 在写入前按设备顺序使用 `FOR UPDATE NOWAIT` 领取本子批次现有通知行，并给新增行冲突设置 100 毫秒锁等待上限。遇忙回滚整个子批次，原始事件、片段、游标均保留，稍后重试；不会绕过占锁设备或标记完成。数据库回放覆盖通知行占锁时快速返回、游标仍为零，以及释放锁后的连续推进。该措施处理回填引入的锁环，不代表其他身份写入之间的锁竞争已全部消除。
