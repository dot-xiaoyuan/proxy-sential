## 结论

**P0 尚未解决。队列扩大后，数据更多地留在持久队列里，但两个串行处理环节仍低于输入。** stream3 已实际启用，消除了被动发现的逐事件紧凑键写入；剩余瓶颈不能再归因于“新版本没启动”或“还没排完旧段”。

1. 发现链路同时维护 stream 事实/状态与消息总线事实/台账，两条链路在同一个 PostgreSQL、同一块旋转盘上重复处理同一批观测。当前台账聚合存在先生成空态、再删除的路径，实际写入成本很高。
2. stream 状态发布使用全局事务锁保护结果版本提交顺序；取得锁后还要唤醒识别、写变化历史和清单、等待提交。别的状态发布者被这些后续工作一起阻塞。现有代码只有一个被动投影 worker，直接增加消费者也不能绕过全局提交顺序。
3. 采集的唯一持久化 writer 仍串行执行多文件 journal 正文、状态、acklog 和游标的耐久提交。即使扩大后端持久缓冲，也不能绕过位于它之前的 journal 写入瓶颈。
4. 大部分抽样事件是重复观测，但仍更新索引较多的事实行，并触发状态生成和识别脏标记。stream3 只消掉一类逐事件写入，没有消掉剩余写放大。

- `publish_state`：约 213.9 秒，中位约 5.26 秒/段，最大 21.43 秒。

- `write_facts`：约 8.3 秒；新段不再出现旧的 `reserve_keys` 慢阶段。

阶段日志只打印至少 100 毫秒的阶段，边界可能包含未完成段；这些是耗时分布，不是完整事务剖析。`publish_state` 包含状态生成、全局锁、状态 SQL 和识别唤醒，不能把整个数字都说成某条 SQL。

`internal/discovery/stream_state.go` 的 `publishStreamDiscoveryStates` 取得 `pg_advisory_xact_lock(9184,213)`，直到整个事务提交才释放。随后 `stream_projection_db.go` 仍调用识别脏标记、变化历史、清单写入。该锁是为了避免序列号先分配后提交导致当前台账游标漏读，**不能直接删锁或仅增加并发**。

19:58 的五次活动采样共出现 142 个 `LWLock/WALWrite` 样本，另有全局 advisory 锁排队；同一后端会被重复采样，不能理解为 142 个独立请求。20:03:53 再次看到两条 `9184,213` 等待，被仍在做识别绑定查询的事务阻塞。19:57:58–20:00:31 的参数化双整数 advisory 调用累计等待约 315.7 秒，来自并发连接，不能当作 153 秒墙钟内的占用比例，也不能将所有参数组合都归为同一个锁。

同一统计窗口，变化历史 INSERT 的累计执行时间约 33.5 秒，其中 PostgreSQL 块读取计时约 30.9 秒。剩余开销包含真实数据页/索引访问及共盘等待，不是只剩 CPU 计算。

### 双套事实与台账写放大

本地 journal 完成后，一路直接执行 stream PG 投影；另一路发布到 Redpanda，由 eventbus consumer 写另一套 PG 事实及 ClickHouse 数据，再由 current aggregator 组合 stream 状态、事件总线事实并写 Redis。总线确实有业务消费者，也参与当前台账读取，但它没有替代原来的 journal/stream PG 路径。

eventbus facts 与 current 的主要相关 SQL 合计生成约 **1.21 亿字节 WAL**，同期全库 WAL 增量约 2.31 亿字节。表统计和 SQL 统计刷新存在边界差，不能强行逐行对齐。这个结果足以说明双路维护是重要负载，尚不能单独断言停掉某条服务就能解决吞吐；当前页面依赖它们，不能按名字含 `shadow` 就停用。

聚合器 `aggregate` 依次执行 stream 文档补入、总线事实汇总、stream 事实补入、空当前态删除。`upsertFactCurrent` 即使某设备全部事实过期，也会先插入空态；`pruneChangedCurrent` 随后可能删除。20:03:53 对下一批最多 1,000 个事实对应的 **398 个设备键**做只读探针：394 个没有 current 行，152 个只含过期总线事实且没有活跃 stream 文档。这证实下一批有较多空态写入候选；是否全部会在同一事务删除，还取决于最后一项有效 stream 事实检查，未作逐行写入追踪。

此外，`allKeys` 由 changed/expiry/stream 三份键列表拼接，stream 补入 SQL 直接 `unnest`。重叠键会重复参与聚合，这是需要有界本地回放核对的候选问题，本轮没有据此宣称现场计数已经错误。

### 重复观测与 journal 成本

首三个 stream3 段共 3,000 条事件，清单中 **2,782 条（92.7%）为 repeat_observation**。这是三个段的样本，不能代表全天。重复观测不新增完整语义变化历史，但仍更新事实的新鲜度，进入状态生成，并可唤醒识别。

现场事实表有 9 个索引、状态表有 9 个索引；累计事实更新约 4,149 万次、状态更新约 2,655 万次，两者 HOT 更新计数均为 0。最近 153 秒的相关更新也没有 HOT 更新。不能把全部索引都认定无用，但频繁更新其排序/时间列确实没有获得 HOT 的索引复用收益。

窗口 A 的 journal 累计时间：append 197.1 秒、commit 209.0 秒；commit 内游标持久化约 89.9 秒、状态约 58.2 秒、ack 准备约 45.8 秒、加载核验约 14.4 秒、锁等待仅约 0.62 秒。源码仍是 v1 多文件耐久协议，实验 WAL 未开启。这支持“持久化路径本身饱和”，但现有计时包含编码与 I/O，不能全部归为 fsync。

## 修复顺序建议，尚未执行

1. **先确定唯一事实与台账职责，消除可证明的重复工作。** 给总线事实、stream 事实、当前台账分别列出实际读取者、恢复职责和退役条件；优先处理空态生成后删除、同批重复键、未变化事实/状态反复改写。保留首次/末次观测、次数、过期边界、撤销和冲突证据，不以跳事件减负。已经有权威用途的链路不能直接停止。
2. **缩小状态发布串行区，再设计分区进度。** 查清并迁出全局版本锁之后可前置或异步完成的工作；长期用按业务键/分区的完成进度与未完成缺口替代跨全网提交串行化。识别唤醒、历史写入与状态可见性必须保持恢复和一致性，不能简单删除锁或调大 worker 数。
3. **处理持久接收的独立吞吐缺口。** 评估让现有消息总线承担权威耐久接收并安全退役重复 journal，或采用有组提交能力的日志/独立 SSD 热路径。必须先把来源位置、重复、乱序、崩溃恢复、ACK 和原文责任说明白；扩大缓冲或关闭同步不能算修复。2000 事件批次仅是候选参数，不能在目前数据库串行成本下假定翻倍批量即可达标。
4. **统一整条链路的版本清单和发布覆盖范围。** eventbus consumer、current aggregator 仍固定旧目录；修复必须核对实际执行文件，不能再次只更新主包就宣称消费链已更新。

下一次代码修改前只需针对已确认的浪费路径做小规模回放和成本核算，不需要完整快照或现场压测。发布前同时给出“减少哪些持久写入/锁占用”“如何保持证据与恢复”“为何能覆盖实测输入”三项依据。一次更新后若仍净积压，停止继续发包并重新分析。
