# 开发时间线

## 总体周期

- 8 周完成 Suricata MVP。
- 12 周完成 AF_XDP/Rust PoC 评估。
- 16 周完成架构定型。

## 第 0 周：目标和边界

目标：确定 MVP 边界，不直接进入底层框架开发。

任务：

- 明确部署形态：旁路镜像口、网关内联、认证系统旁挂。
- 明确性能目标：1Gbps、5Gbps、10Gbps，峰值 PPS，允许延迟。
- 明确策略动作：只记录、告警、降速、踢线、封禁。
- 准备测试流量：正常终端、手机热点、路由器共享、模拟器、加速器、下载器。

验收：

- MVP 默认旁路检测。
- 默认影子模式，不直接处罚。
- 至少准备 5 类可回放测试样本。

## 第 1 周：Suricata 实验环境

目标：拿到稳定的原始网络事件。

任务：

- 部署 Suricata。
- 开启 EVE JSON。
- 采集 flow、dns、tls、http、quic。
- 跑离线 pcap 和短时真实镜像流量。
- 记录 CPU、内存、丢包、事件吞吐。

验收：

- 能稳定输出 EVE JSON。
- 能看到 DNS query、TLS SNI、JA3/JA4、HTTP Host/User-Agent、flow。
- 能按源 IP 聚合事件。

## 第 2 周：标准事件模型

目标：解耦采集后端和业务逻辑。

任务：

- 设计 NormalizedEvent。
- 实现 `suricata-adapter`。
- 支持从文件和 stdin 读取 EVE JSON。
- 输出 JSONL 标准事件。
- 增加事件回放命令。

验收：

- Risk Engine 不依赖 Suricata 字段。
- 标准事件包含 source、type、timestamp、src_ip、dst_ip、flow、payload、confidence。
- 原始事件可追溯。

## 第 3 周：证据聚合器

目标：从事件生成证据。

任务：

- 实现按 IP 的滑动窗口。
- 实现基数统计和去重。
- 实现第一批 Evidence：
  - 多 User-Agent。
  - 多 JA3/JA4。
  - TTL 多簇。
  - DNS/SNI 多样性异常。
  - 目的端口分布异常。

验收：

- 每个 Evidence 有类型、窗口、分数、置信度、解释。
- 支持回放测试。
- 支持查看某 IP 的证据时间线。

## 第 4 周：风险评分 MVP

目标：输出可解释风险分。

任务：

- 实现规则评分器。
- 实现风险等级。
- 输出 RiskSnapshot。
- 支持规则配置热加载。
- 加入负证据：加速器、模拟器、测试账号、白名单。

验收：

- 风险输出包含 evidence_ids。
- 支持正常、可疑、高风险、确认代理四级。
- 能对回放样本生成稳定结果。

## 第 5 周：API 和最小 UI

目标：能查看、解释、标注。

任务：

- API：
  - `GET /ips/{ip}/risk`
  - `GET /ips/{ip}/evidence`
  - `GET /risks`
  - `POST /labels`
  - `POST /rules/reload`
- UI：
  - 风险 IP 列表。
  - IP 详情页。
  - 证据时间线。
  - 原始事件样本。
  - 人工标注。

验收：

- 能解释每个判定。
- 能标注意见。
- 能导出样本用于复盘。

## 第 6 周：影子模式测试

目标：接真实流量但不处罚。

任务：

- 接入真实镜像流量。
- 连续运行 7 天。
- 每天抽样复核高风险、可疑和正常样本。
- 记录误报来源。

验收：

- 高风险样本人工确认率达到可接受水平。
- 输出 Top 10 误报类型。
- 记录吞吐、延迟、积压、资源占用。

## 第 7 周：策略闭环

目标：让检测结果能进入处置链路，但保持灰度。

任务：

- 实现影子模式、只告警、降速、踢线动作。
- 接入用户组、产品组、白名单、冷却时间。
- 所有动作写审计日志。
- 支持一键撤销。

验收：

- 能按用户组灰度。
- 处罚动作可追溯。
- 误报可撤销。

## 第 8 周：MVP 评审

目标：决定是否继续 Suricata，还是启动自研 sensor。

评审问题：

- Suricata 输出信号是否足够。
- 性能瓶颈在采集、解析、存储还是风险计算。
- 哪些证据真实有效。
- 哪些规则误报最高。
- 是否需要低延迟自研数据面。

## 第 9-12 周：AF_XDP/Rust PoC

目标：验证自研高性能数据面。

任务：

- Rust 实现 AF_XDP sensor。
- 解析 L3/L4、DNS、TLS ClientHello、HTTP Host/UA。
- 输出同一套标准事件。

## 当前完成状态：生产形态影子观测第一版

已完成主链路：

- 30 机器 Suricata 常驻采集镜像口，EVE 持续写入。
- `proxy-sentinel-shadow.timer` 每 10 分钟读取 EVE 增量，生成标准事件、证据、风险快照和风险列表。
- PostgreSQL 保存业务状态，ClickHouse 保存标准事件和采集诊断，30 机器使用 `dual` 模式。
- 控制面 API 和前端已支持总览、风险列表、IP 详情、采集诊断、访问态势、shadow runs 和审计展示。
- 本地前端可关闭 mock 后通过 CORS 直连 30 的真实 API。

## 下一阶段推进顺序

1. 事件检索与访问对象钻取：补齐按时间、IP、域名、UA、端口、协议的标准事件检索和详情页。
2. 人工复核闭环：labels 写入 PostgreSQL，审计落库，风险 IP 展示复核状态。
3. 前端运营体验：自动刷新、数据更新时间、空态/异常态、移动端卡片化和真实 API / mock 状态区分。
4. 实时 ingest：新增常驻 worker，让标准事件入库接近实时，风险评分继续窗口批处理。
5. 规则治理和生产硬化：负证据、规则版本、多 sensor、认证、备份、TTL、监控告警。

验收：

- 事件检索可以直接回答“谁在什么时间访问了什么对象”。
- 复核结果可以回流展示和后续风险判断。
- 30 机器从测试部署演进为可复用的生产部署模板。
- 和 Suricata 并行跑同一段流量。
- 对比事件覆盖率、CPU、丢包、延迟。

验收：

- 标准事件兼容。
- 关键事件覆盖率接近 Suricata。
- 性能收益明显。
- 运维复杂度可接受。

## 第 13-16 周：架构定型

可选结论：

1. Suricata 够用：保留 Suricata，强化风险模型和运营后台。
2. Suricata + 自研轻 sensor：Suricata 做深解析，Rust AF_XDP 做低延迟轻量信号。
3. 全自研 Rust 数据面：仅在高吞吐、低延迟、强定制需求明确时采用。
