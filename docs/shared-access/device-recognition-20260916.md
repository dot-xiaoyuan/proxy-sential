# 设备画像链路修复（2026-09-16）

## 部署结果

已部署 `.30`：`2026.09.16-device-lease`。未备份或回填历史数据，未连接认证系统，未启用处罚。现有前端不变。

修复内容：

1. Zeek 记录 DHCP 选项序列、Vendor Class、ACK 时间；标准适配保留租期及这些字段。使用现场 Zeek 的 DHCP::aggregate_msgs 接口，未让画像引擎直接依赖抓包字段。
2. 新增独立设备地址租约表，不把最后观测时间改成未来时间，也不生成账号身份。只有含明确 ACK、有效 MAC、分配地址、ACK 时间及有限租期的记录参与归属；缺少证据保持未知。超过七天的租期暂不接受。
3. 按传感器、园区、IP、事件时间匹配，后续 ACK 替换旧绑定，同一时刻冲突不归属；释放、NAK、DECLINE 停止对应终端租约。乱序和重复记录不会改变事件时间判断。源观察未配置园区时使用空园区，不能跨传感器兜底。
4. 异步画像任务先处理新增 DHCP/带 MAC 的设备事件，再关联域名线索；软件事件可使用唯一有效租约，mDNS 查询名不直接当作本机身份。
5. 所有处理进程通过配置加载已安装完整指纹库，修复控制面使用完整库、部分后台进程使用内置小库的差异。
6. 修复同批事件属性丢失、后续稀疏信号覆盖完整画像的问题；基于已合并属性计算画像。
7. 历史停用配置现在同时覆盖独立画像补扫，避免启动七天扫描阻塞实时队列；队列只接收设备和可识别域名事件。此模式不修补旧数据，队列仍有上限，溢出或连续失败需要单独诊断，不能声称零丢失。现场部署后的观察期未再看到原画像补扫超时。

## 现场观察及限制

上线后已收到真实新增租约，终端画像继续更新。末次统计见 `artifacts/device-recognition-20260916/field-final.txt`。观察中持久化厂商字段由 18 条增长至 56 条，终端总数由 92 增长至 107；分母与新流量同时变化，不作为固定集识别率提升报告。

整机品牌、型号仍为 0。现场域名归属尚未出现成功记录；已检查的早期租约对应 IP 最近三分钟没有 DNS/TLS/HTTP 事件，因此不能用该观察窗口宣称域名归属现场验收通过。相关正确性目前由隔离回放/数据库测试证明，后续真实新租约与域名命中还需现场验证。

有效租约从本次部署后的 ACK/续租开始建立，旧 DHCP 点记录不自动扩展为有效租约。现有 537 条 DHCP 指纹快照较旧，633 条 UA 规则仍不能单独推断整机品牌；完整品牌/型号覆盖提升尚未完成。后续应以实际未命中的设备信号补规则或增强有明确归属的设备服务响应解析，不将 MAC 厂商、浏览器或访问应用直接当作整机品牌。

Zeek 接口依据：[官方 DHCP 文档](https://docs.zeek.org/en/v6.2.1/script-reference/proto-analyzers.html)。详细输出位于 `artifacts/device-recognition-20260916/`。
