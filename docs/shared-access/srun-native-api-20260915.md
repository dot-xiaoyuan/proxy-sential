## 原生契约

- `POST /api/v2/auth/get-access-token`：表单 `appId`、`appSecret`，成功数据含 `access_token`、`lifetime`。鉴权使用 authorization 表中登记的正式应用，不使用特殊绕过标记。
- `POST /api/v2/base/online-drop`：表单 `access_token`、`user_name`、`rad_online_id`、`drop_type`。在线 ID 必须是认证来源原始 ID，不能直接传 Sentinel 的带采集实例复合会话 ID。
- 接入类型为 radius、proxy、dhcp、portal；调用方必须来自受控能力配置，不凭 IP 或端口猜测。
- 服务端先核对账号在线集合中的 ID，再调用对应处理器。返回 `code=0` 仍只是接收结果，不证明在线会话已经消失。
- portal 底层将包含 IP 的下线指令写入队列。此能力仍需处理排队期间身份变化的风险，不能直接宣称符合账号级准确处置要求。
- `/api/v2/base/online-data` 的 `searchParams` 是输出字段选择，只输出 user_name、group_id、ip，并非账号查询过滤器。它没有原始会话 ID，且分页没有固定快照，不能用于精确完成核验。

核对依据是 190 `/srun3/www/srun4-api/` 下的 v2 AuthController、Authorization，v1 BaseController、common/extend/RedisPagination.php、common/models/Common.php 和 KernelInterface.php。v2 基础控制器继承对应 v1 实现。

## 2026-09-16：撤销后继续对账

接入检查复现了协调器的另一处问题：授权撤销会同时阻止已发送动作的只读对账，使旧动作结果无法继续确认。新增不创建发送权的 `Journal.Lookup`，严格匹配完整不可变意图；已登记动作仅进入观察路径，不再要求新的发送授权，不再次发送。未登记动作仍必须通过授权和后续检查才能登记并发送。
