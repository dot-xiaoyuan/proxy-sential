# 存储效率与重复历史审查（2026-10-24）

本文按“标准事件 → 证据聚合 → 风险评分 → 仅记录的策略闭环”和设备中心查询需求审查当前设计，给出后续实现顺序。它不是已经部署的改造，也不是容量达标证明。代码依据为本工作区当前文件；现场容量来自 2026-10-24 对 `222.204.3.184` 的只读查询，现场应用当时仍为 `2026.10.24-discovery-ui1`。PostgreSQL 行数是统计估值，ClickHouse 行数和磁盘字节来自 active parts；不能由这些累计数推断峰值写入速率或两表逐行相同。

## 1. 功能所需的最小数据职责

| 职责 | 必须保留的内容 | 不应长期保留的内容 |
|---|---|---|
| 采集、重试 | 来源、作用域、批次/事件 ID、内容哈希、首次入库时间、未完成缺口；跨存储确认前的一份可恢复原文 | 每个消费者各自一份无期限完整批次；完成任务仍作为长期原文仓库 |
| 标准事件与证据 | 每个必要事实的一份权威原文、语义版本、完整来源与校验；案件引用独立保护 | 物化视图中重复的 `observer_json/payload_json/flow_json` 全文；按协议复制整条标准事件 |
| 身份、地址和发现 | 当前有效关系、最后观测、历史变化及冲突；相同事实的首次/末次观测和次数；撤销与更正 | 每次相同广播都追加一份完整历史，或仅因心跳而重写整个设备状态 |
| 风险与策略 | 有证据引用的评分/决策版本、解释、审计和“仅记录、未执行”动作与上报记录 | 在决策、执行、观察、案件和归档中各放一份同样的原始流量或全量证据数组 |
| 页面和统计 | 有界当前读模型、结构化索引、独立统计及可追踪的新鲜度 | 请求内扫历史、全网聚合；为小字段查询复制大 JSON |

“相同”按作用域、来源、业务键、语义版本和规范化内容判断，不能仅按 IP、MAC 或哈希合并。两次相同 DHCP/服务公告仍可能证明持续可见，应保留必要的观测时间、次数或时间区间；内容更正、撤销、不同来源、会话边界、冲突、案件引用绝不能合并掉。哈希只做索引和快速比较，冲突时要核对原文。每一份派生表可以因查询而存在，但应存足够的标量和原文引用，不应默认复制完整正文。

## 2. 现场容量和链路对照

现场 PostgreSQL 重点表（约 GiB，包含索引和 TOAST）：`policy_decision_records` 30.6／约 451 万行，`shared_behavior_observations` 10.6／360 万，`identity_ip_mac_history` 8.3／1386 万，`device_name_evidence` 4.1／428 万，`identity_applied_events` 3.7／355 万，`identity_ingest_batches` 3.0／103 万，`discovery_changes_202610` 2.8／137 万，`identity_delta_members` 2.1／11.6 万，`shared_device_profile_history` 1.8／118 万，`discovery_batch_work` 0.66／1.17 万。策略决策表主体约 1.19 GiB、索引约 2.70 GiB，其余大头在 TOAST；这说明大文档值得优先抽样，但不能由此断言所有策略记录重复。发现任务表主体只有约 3.3 MiB，约 0.66 GiB 总空间主要是大字段及其存储开销，符合整批 JSON 暂存的结构。

现场 ClickHouse 重点表：`normalized_events` 4945 万行／21.7 GiB，`identity_signal_events_v1` 5744 万／13.3 GiB，`passive_discovery_events_v2` 1.38 亿／9.1 GiB，`router_signal_events_v1` 1429 万／8.9 GiB，`shared_observation_events_v2` 476 万／7.5 GiB，`normalized_event_features` 4922 万／1.85 GiB，`discovery_evidence_archive` 156 万／0.28 GiB。前五项并非直接相加得出“重复量”：它们覆盖范围和保留期不同；但迁移定义确认多张物化视图复制了标准事件的多个完整 JSON 字段。

另有 `shared_behavior_signal_events_v1`、活动图 5 分钟/小时/日事实表及特征表。它们属于提取特征或预聚合，需按实际读取方、维护成本和 TTL 单独评估，不可因为行数多便删除。已有 [ClickHouse 迁移 041](../migrations/clickhouse/041_retire_unread_derived_tables.sql) 删除了误建的第二个相同物化视图（曾将同一结果写两遍）及无读取方的 `ip_event_features_10m`，是重复写入和无用结果表会显著增加合并负载的实际例子。

## 3. 已确认的结构问题

### 3.1 发现：每段重新读取整批、每条反复写状态

[发现任务领取](../internal/discovery/pipeline_lease.go) `RETURNING w.events`；[处理器](../internal/discovery/pipeline.go) 每次解码全批，再只处理最多 50 条。一个 2,000 条批次最多需 40 次传输和解码同一 JSON。受理上限按条数而不按序列化字节数，巨大事件会突破预期内存/事务预算。

每条事件还单独查询回执、查询事实、UPSERT 事实、插入回执；即使语义哈希未变化也会更新事实及设备 `touched` 集合。每个受影响设备随后读取最多 1,025 份完整事实 JSON、重新分类并无条件改写整份 `discovery_device_state_v2.document` 和结果版本。`discovery_device_changes_v2` 对晚到或语义变化仍写完整观测 JSON，而 ClickHouse `discovery_evidence_archive.document` 也保存完整标准事件。重复公告因此放大 PostgreSQL WAL、索引和 TOAST 写入；同一事务里的逐事件往返、锁和远端归档又叠加在 3–4 秒处理预算内。

此前仅 DNS-SD 的约 35 秒新输入试运行产生 4,825 条事件，停止时尚余 4,375 条，出现 6 次 `deadline_exceeded`；这是新数据，不是历史回填造成的。多次试运行记录与阶段耗时见[现场恢复记录](discovery-recovery-184-20261024.md)。现有事实可以定位写放大与超时关联，但尚不能单凭表大小确定 PostgreSQL、ClickHouse 和网络各占百分比。

### 3.2 身份：可靠性结构合理，载荷与重复当前态偏重

[身份收件箱](../internal/store/identity_inbox.go) 将整个 `normalized_events` 数组写进 `identity_ingest_batches`，续领按进度再次读取并解码整批。它保护跨存储恢复，不能直接删除；应改为有界片段，完成并核验权威落点后回收暂存正文，只保留小型批次与缺口账本。`identity_applied_events` 的事件级回执用于幂等，不能按“历史重复”简单清除，应测算其保留窗口、恢复上界和索引成本。

`identity_signal_events_v1` 物化视图又从 `normalized_events` 复制 `subject_json/observer_json/payload_json/flow_json/raw_ref_json`，8 天 TTL 与原表 7 天 TTL 有 7 天重叠。身份查询或归档如需 8 天可留一份权威正文，但另一表应尽量为结构化窄索引。身份快照的 `identity_delta_members` 每运行保存完整 `document`，随后 `identity_delta_changes` 也保存文档；代码对完成 24 小时后的运行按 500 行清理。其现场约 2.1 GiB／11.6 万行，需要核对完成运行清理是否追得上，不能把正在处理的快照临时数据误作无用历史。

### 3.3 协议和风险：多份全文、归档再打包

`passive_discovery_events_v2` 和 `router_signal_events_v1` 的物化视图都复制了标准事件的多个 JSON 字段；前者按事件发生时间保留 30 天，后者 8 天，而原始 `normalized_events` 为 7 天。被动发现旧读取链路还从 ClickHouse 取完整 `payload_json`，再写 PostgreSQL `discovery_observations`；新 V2 则写 `discovery_service_facts_v2`、设备状态和变化表。两套消费者/读模型的职责若未明确，容易对同一输入重复建模。先核对实际页面、案件和协议读取方，再收敛为一个事实所有者，不能先停其中一条导致功能退化。

`shared_observation_events_v2` 保存握手/覆盖事件的 `payload_json`，迁移明确暂不设置破坏性 TTL；归档器在 30 天后按决策重读原始事件，组装 `shared_observation_archive_v1.document`，核验后删除部分 PostgreSQL 热数据。源事件表并未随已确认归档自动清理，且不同决策的归档包可能再次包含相同原始事件。这是必须先证明引用完整性、再设计单份原文与引用关系的高优先级生命周期问题。`policy_decision_records` 和 `shared_behavior_observations` 的完整文档有独立审计/当前读取价值，不能直接去掉；但决策记录、观察历史和归档包中重复嵌入的证据应尽量转为稳定引用、窄摘要和内容哈希。策略“仅记录”动作/上报仍必须单独保留其执行状态与审计记录。

### 3.4 其他历史和读模型

`identity_ip_mac_history`、`account_sessions`、`account_identity_session_projection`、`device_name_evidence`、`shared_device_profile_history` 的行数都大。前两者包含不同的地址/会话语义，投影是当前查询入口，不能直接视为重复；名称证据按事件键留完整 `evidence`，需检查同名重复广播是否造成无意义全文增长。共享设备档案已有 `sharedProfileProjectionChanged` 才追加历史的保护，但每次刷新仍会 UPSERT 完整当前行；需要增加“当前行无变化不写”的核验。读模型应只因语义状态或必要的新鲜度变化更新，并将列表与详情的全文读取分离。

## 4. 目标结构与处理算法

1. **一份权威正文，多份窄索引**：按业务类型确认原文拥有者、主键/版本、保留起点、归档与案件保护。ClickHouse 仅对需要全文的事件保留一份规范原文；协议/身份/风险物化视图优先保留查询所需的标量、事件引用和内容哈希。PostgreSQL 当前事实、状态、决策与任务保留自身必要业务字段，不再嵌套整条源事件。源表可能只有 7 天 TTL，而目标证据要一年时，必须先建立并验收足额的唯一长期原文归档，不能直接改窄表或删除旧表。
2. **暂存按段读取和释放**：入库时按字节与条数切成小片，任务账本保存批次哈希、片段顺序、已确认前缀及缺口。领取只返回当前片段；跨存储确认、投影回执、冲突校验完成后清除该片段暂存正文，保留小账本及必要回执。读取/网络/内存成本随本次片段增长，不随原批次长度增长。失败片段和未核实的最后一份原文不清理。
3. **同一事务内合并业务键**：将事件级验签/回执与事实更新分开；先按 `(作用域,设备,来源,事实键)` 归并本段候选，只对真正改变的事实写入。相同内容的重报更新紧凑 `last_seen/count/有效期`，不追加全文历史；同一段设备状态最多更新一次。变化历史记录差量、旧/新哈希、原因与证据引用，实际业务变化需要时可存最小快照。回执仍逐事件可追踪，冲突仍拒绝，晚到、撤销、更正和过期独立处理。
4. **有界设备状态维护**：为事实建立结构化有效性、分类候选和有序读取索引；普通输入只更新影响的候选和聚合计数。极值失效时查同设备/同字段的下一个候选，不加载该设备全部历史或全部事实 JSON。结果版本只在页面可见语义变化时递增；纯心跳只更新其必要新鲜度字段，按定义触发查询可见性。
5. **冷热与审计分离**：热查 30 天和一年归档针对必要、去重后的设备证据，均以首次成功入库计时；长期保留范围不等于重复正文全部保留一年。归档采用引用清单、哈希与覆盖检查；复制期间允许暂时两份，验收后退役过渡副本。案件可引用唯一归档对象并有独立保护，不能用关联删除级联清掉唯一证据。普通流量明细仍按各自 TTL。
6. **避免全量历史常态化**：实时、快照差量、规则重算、修复和统计使用不同队列与预算。快照按键排序归并，只处理变化成员；完整重建仅用于一次性迁移/修复，限速、可中断并公开缺口。用户授权的新鲜起点可审计取消旧任务，不能把它们记作已处理，也不能据此宣称历史完整。

不建议先引入新消息队列或直接放宽超时。当前最热路径中的全批重复读取、逐事件事务往返、无变化改写和全文复制，即使换队列仍会存在。也不能用“每分钟批量合并”偷换 5 秒可查询要求；应以小段、有限字节和受影响键做到实时处理，并逐条测量入库到查询反映的延迟。

## 5. 改造顺序与验收

| 阶段 | 先完成的工作 | 必须证明的结果 |
|---|---|
| A：量化 | 只读统计各表正文、TOAST、索引、TTL、增长速率、重复内容比例；追踪每种原文的读者和案件引用。按事务记录事件数/字节、SQL 次数、WAL、CH 归档耗时、锁等待、重试与查询延迟 | 区分“行数多但业务必要”和“重复全文”；给出真实流量下单位事件成本及主要瓶颈 |
| B：发现实时链 | 先写重复/乱序/更正/撤销回放，再做片段领取、同键归并、回执批量化与状态条件更新；保留旧读写作为回退 | 相同输入不多写全文变化，状态仍准确；不再每 50 条解码整批；新输入净消化、零数据缺口，逐条 5 秒可查和超时/资源达标 |
| C：身份与快照 | 对身份收件箱分片，核实临时正文清理；核对快照 delta 表的完成与清理速率 | 故障恢复及幂等不退化；重复快照只产生变化成员写入；暂存正文不无界累积 |
| D：存储收敛 | 对每个 CH 物化视图列出实际查询；先建窄索引/唯一原文与引用，再影子比对、切读、验证归档覆盖，最后退役旧全文副本 | 同一事件的长期全文只剩必要的一份；查询、案件、策略审计与保留语义完整；合并读取、WAL 和占用按实测下降 |
| E：协议扩量 | 仅在 B–D 的相关依赖通过后，按单协议受限输入逐批开启 | 每批观察输入/消费净值、积压、错误、5 秒可查、资源和查询延迟；不靠加并发或跳任务掩盖不足 |

迁移均新增版本，不改写已应用迁移；双写或双读期间的临时副本在验证后明确退役。需要回放“同内容不同时间、不同来源、相同事件 ID 不同内容、晚到、撤销、跨批重试、归档部分成功、进程中断、案件保护”，并比较旧新结果、回执和未完成缺口。验收报告须区分本地回放、184 真实观察、待核实的容量上限。当前只完成设计审查与规则修订，未修改代码或现场存储，未恢复新增 Zeek 协议。
