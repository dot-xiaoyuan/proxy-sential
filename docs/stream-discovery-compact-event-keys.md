# 流式发现紧凑事件键：兼容阶段与切换门槛

## 依据与目标

184 的 r34 在 2026-11-01 17:54–18:34 连续观察中，四轮被动采集都达到 256/256 满队列，发生三次自动重启；续采确认第四次重启。投影队列长期为 64/64，`projection.write` 常为数秒一段。只读 PostgreSQL 快照显示旧全局事件键台账约 2,003 万行、总量 9,466 MB，其中主键索引约 4,636 MB。旧表主键包含三个文本字段，新事件的逐条唯一索引写入是明确的成本；这组快照不能证明它是唯一瓶颈，也不能预测新索引的现场收益。

本方案保留逐事件去重、跨月重放、原月份回执定位和冲突拒绝语义，用固定 32 字节摘要缩小新键的主索引。完整的代次、作用域、事件键、内容哈希、首次接收时间和回执月份仍在表行中；摘要冲突必须核对完整键，不能当成同一事件。

## r35 兼容阶段

- PostgreSQL 迁移 214 新建 `stream_discovery_event_keys_compact`、摘要函数和按首次接收时间的 BRIN 索引；旧台账、回执及原始证据不改写。案件证据触发器与 Go 读取均接受任一台账，但双写记录若哈希或月份不一致则拒绝引用。
- 被动采集继续生成原来的 `stream-` 事件号。命令行认识 `--passive-compact-event-keys`，但此版本明确忽略它，避免应用从后继版本回退时因旧参数无法启动或继续产生新格式。
- 本版本能够读取、投影、确认 `stream2-` 段；投影新键时在同一 PostgreSQL 事务写紧凑和旧台账。回执查询先查紧凑台账，仅在完整身份不存在时有界回查旧台账，以兼容其他来源曾使用相同前缀的键。
- r35 本身不产生新格式，也不减少正常被动流量的旧索引写入，不能据此宣称吞吐改善。r35 回退到 r34 时，正常生产路径仍只有旧格式。

## 后继切换与回退

只有在 r35 的真实迁移、读取及回退兼容已验收，且 `previous` 明确为 r35 时，后继版本才可单独启用 `stream2-` 生产和紧凑台账单写。后继版本必须把生产开关同时传给投影写入选择；关闭开关时仍能处理已有 `stream2-` 段。运行中新键落入紧凑台账后，应用只能回退到能处理该台账的 r35，不能回退到 r34。r35 对回退期间未投影的 `stream2-` 段双写两账本；已投影的段按已有投影标记和紧凑台账继续确认，不能重复改写事实。

切换前还需验证旧台账中有无相同作用域的 `stream2-` 键，排除历史前缀冲突。非被动来源的新输入在 `CaptureStreamOnce` 准入时由 `assignStreamPositionKeys` 将事件号统一改写为 `stream-` 加来源位置哈希；即使上游原始号以 `stream2-` 开头，也只在 `producer_event_id` 中保留原号，不能新占用紧凑键前缀。旧段恢复直接读取已持久化的标准事件，跳过来源位置重写；共用回执验证仍允许其原有前缀，避免阻断合法未确认段。切换与关闭均不能重置来源游标、确认标记或未处理段。

r36 把 `--passive-compact-event-keys` 作为默认关闭的运行时开关：开启时采集生成 `stream2-`，同一配置使投影只写紧凑台账；关闭时生产旧键，投影仍能双写未完成的 `stream2-` 段。共享采集配置文件不能启用该运行时格式。开启前，进程以只读查询确认紧凑表和摘要函数存在，缺失则在启动采集前报错。**发布预检必须确认 r35 兼容版就是应用回退目标**；进程启动时不读取 `previous` 链接，因为应用切换和健康检查期间该链接的更新时序不保证可用。r36 的全仓 Go 测试、相关包 race、构建、vet 和 Linux amd64 编译通过；184 已按单独授权启用开关，实测结果见下文，应用回退演练与长期存储生命周期仍未完成。

r36 也可从发现服务专用的 `discovery.env` 读取 `PROXY_SENTINEL_PASSIVE_COMPACT_EVENT_KEYS=true` 作为上述命令行开关的默认值；空值和 `false` 保持旧格式，非法布尔值使进程拒绝启动。现场在保留 `ExecStart`、备份原配置后单独激活；通过恢复原文件及重启关闭。r35 不读取此环境变量，应用回退后仍生产旧键；此前已接收的 `stream2-` 段由 r35 兼容投影处理。184 的原配置字节副本及启用时间记在 [当前工作记录](current-work.md)。

## 存储成本与生命周期

新主键索引的读取收益是按摘要快速定位全局事件键和原始回执月份；写入仍为每个新事件一条 PostgreSQL 行、一次唯一索引维护以及摘要计算。BRIN 仅为按首次接收时间扫描提供低写入成本的准备，不会自动清理。结果失效由不可变事件键和同事务回执状态决定，不使用缓存。旧表与新表目前都没有完成“热查 30 天、归档至首次入库后一年”的核验归档及安全清理闭环；`stream_discovery_receipts` 也没有未来月份分区维护，会在已预建月份之外进入 default 分区。不能因新索引存在而缩短保留期或直接删除去重键。

逐事件键拦截同一事件换段重放；`stream_projection_segments` 仅按段 ID 去重，不能替代它。安全退役需要先核验原文、回执和变更历史归档的覆盖范围与哈希，再建立可持久核验的来源位置水位或完成代次受控关闭、清空待办，之后才能有界清理对应键。`archive_state=confirmed` 只说明三条处理 lane 已确认，不能当作归档覆盖核验。案件引用原文继续独立保护；没有上述证明时新旧键都必须保留，容量测试应包含持续增长和后续清理成本。

### 段完成见证（r37 已发布）

迁移 215 为已有 `stream_projection_segments` 增加可空的来源文件号、起止偏移和 lane 完成时间，不新建索引；表锁等待上限为 5 秒，超限时迁移失败且应用不得切换。新投影段在原事务里携带来源位置；旧投影行保持空值，不能事后补作完成证明。所有必要 lane 与共享、风险后续入队成功后，finalizer 才对新行幂等写入完成时间；未知提交结果保留 journal 段，重试时读取同一来源位置确认，冲突拒绝。旧行沿用原释放流程，但不纳入未来清理依据；无投影的段不依赖此表。

这一行只为后续按段审计提供定位和已完成处理步骤的见证，**不证明 ClickHouse 原文、PostgreSQL 收据及变更历史的归档覆盖**，也不启用键、收据或案件证据清理。[段完成见证与归档覆盖审计](stream-projection-coverage-audit.md)给出当前有界只读核验入口及尚缺的来源清单、原文和案件证明。读取收益是能按现有代次/投影时间索引有界核对来源位置；写入成本是每个新投影段多一笔 PostgreSQL 更新事务。现有表没有新的失效策略，见证与段投影记录同寿命，安全退役须以后续独立归档覆盖及来源水位核验为准。r37 已在 184 以 `--skip-backup --prepare-only` 执行真实迁移并切换；13:23–13:45 UTC 的 661 个新投影段都有来源位置和完成时间，旧行未被误标。40 个阶段窗口的 `finalizer.finalize` 602 次平均 1.174 秒，投影段表约 24 分钟总量增 835,584 字节、索引增 253,952 字节，含其他来源及观察窗外时间。没有独立 PostgreSQL 测试库，并发故障恢复、WAL 归因与长期成本尚未验收；见证仍不得用于数据清理。

r36 在 184 的真实输入短窗测得紧凑台账约每万键增长 3.7 MB、主键索引约 0.78 MB；BRIN 当时尚未增长。该成本没有包括收据、原文和归档，不能直接推算一年容量；WAL 计数覆盖全库，也不能全归因于新键。r36 的 40 分钟主观察与后续 10 分钟续采确认旧段排空后投影队列维持低位，相关段写入约 1.1 秒，未再满采集队列或重启；切换前旧段导致的停采缺口仍存在。r37 切换后首个 20 分钟观察中，采集队列峰值 5/256、无重启，投影队列 43→29/64，最近 100 段的 journal 接受到投影 P95 曾约 55 秒；间隔约 9 分钟的第二个 20 分钟窗口中，采集仍未满队列或重启，投影队列 11→0/64，追平时最近 100 段 P95 约 3.34 秒。局部段样本不能代替逐事件查询接口验收，也不能抹去前一窗口的积压。仍需持续监测资源、实际查询延迟、增长和后续清理成本；现场不造数压测，本地数据库栈按当前环境约定停用。若增长、生命周期或持续吞吐未达到约定，保留兼容回退入口，不宣称长期容量达标。
