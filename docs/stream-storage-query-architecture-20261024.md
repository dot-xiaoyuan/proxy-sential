# Zeek/DPI 事件从采集到查询的目标架构（2026-10-24）

## 结论与边界

**决定采用“持久顺序日志 + ClickHouse 批量归档/检索 + PostgreSQL 增量当前态”的双读模型。** Zeek 与 DPI 记录先在采集侧完成解析、作用域判定和标准化；ClickHouse 在正常写入路径只接收已准备好的成批行，不先逐事件查询 ClickHouse 或 PostgreSQL。只有被明确选为设备、路由器、身份或风险事实的事件进入 PostgreSQL 投影；普通流量日志不进入 PostgreSQL 逐事件任务表。设备当前态、案件和策略状态从 PostgreSQL 读，日志时间线与聚合从 ClickHouse 读，证据原文按稳定引用从唯一权威归档取。

```text
Zeek/DPI/被动发现 → 固定来源位点和可恢复原文 → 一次标准化
                                              ├→ ClickHouse：批量正文 + 窄检索/聚合
                                              └→ PostgreSQL：仅选中事实的批量增量投影
页面/API：当前态和案件读 PostgreSQL；协议日志读 ClickHouse；证据按引用取正文
```

这是一份**目标设计和切换判定**，不是已实现或已通过 184 容量测试的结论。具体吞吐、延迟和存储额度须按真实输入测量；如果目标负载超过硬件可持续写入能力，软件队列只能延缓积压，不能让积压消失。用户已明确旧未处理事件不回填；切换采用有审计的新起点，旧缺口不计入处理成功。现场未作任何变更。

### “批量/异步”的准确含义

当前代码并非完全没有批量：[Zeek 文件采集](../internal/realtime/worker.go)按文件块组批，[ClickHouse 写入](../internal/store/clickhousestore.go)用一次 `INSERT ... JSONEachRow` 写多行，[发现链](../internal/discovery/pipeline.go)按最多 50 条的片段处理。问题是一个 Zeek 来源的读取、批次登记、发现暂存、ClickHouse 写入、运行记录、诊断和位点提交串在同一循环；发现片段还在处理前后查询 ClickHouse 归档、核对回执和重算设备事实。代码默认还会在标准事件插入前分块查询已有 event ID。**因此“已成批传输”不等于“写入链没有同步查询和写放大”。**

ClickHouse 官方说明同步插入宜成较大批次；很多小插入会制造 part 与合并压力。低频小流可使用 `async_insert=1, wait_for_async_insert=1` 让服务端合批，但客户端仍等到落盘确认；`wait_for_async_insert=0` 不能作为可靠确认。是否采用异步插入须先核对 184 的 ClickHouse 版本、表设置和物化视图依赖；尤其 26.1 以前异步插入与依赖物化视图的重试去重不能直接视作端到端可靠。参见 [ClickHouse 写入实践](https://clickhouse.com/blog/10-best-practice-tips)、[异步插入说明](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)及 [26.1 修复说明](https://clickhouse.com/blog/clickhouse-release-26-01)。

## 当前链路的具体代价

| 环节 | 当前结构 | 本设计的变化 |
|---|---|---|
| Zeek 输入 | 单个 `Run` 循环依次遍历来源，一个来源的存储等待会延后其他来源；文件位点随跨库写入串行推进 | 每来源独立读取与背压；先把不可再生的输入写入持久顺序日志，后续归档和投影各持自己的确认位点 |
| ClickHouse 原始事件 | `normalized_events` 有完整 JSON；正常路径可能先按 event ID 查询；多个协议/风险物化视图再复制大 JSON | 无逐事件存在性预查；一个事件只进入一个保留类别的权威正文表，协议检索与特征表只保存类型化窄字段和正文引用 |
| 发现处理 | 片段中的归档查询/写入/再查询、回执与事实查询、设备事实全文重读和分类都消耗短处理预算 | 归档是独立批量写入；投影按事件键去重后以集合语句处理，只读取受影响的当前事实与候选，事务不跨 ClickHouse |
| 当前查询 | 已有 PostgreSQL 设备状态游标查询，但仍可能关联事实、读取完整 `document`；日志查询跨多种完整事件表 | 列表只用小型状态/检索行；详情按页取事实和变更；需要原文才用稳定引用去 ClickHouse；统计独立 |

上述是代码结构事实，不是各环节耗时占比。2026-10-24 的[存储审查](storage-efficiency-audit-20261024.md)记录了重复全文表和历史现场容量；这些数字是当时快照，不代表现在的 184 状态，也不能推算未来协议全开后的写入速率。

## 一、输入、事件身份与持久边界

1. **来源独立**：Zeek 每种日志、每个文件和直接被动发现各有读取器、文件身份与连续字节位点；读取器之间不能因某一路 ClickHouse 或 PostgreSQL 慢查询串行阻塞。记录捕获域、sensor/site、接口、VLAN/QinQ、来源协议和采集代次；作用域缺失的事件隔离为解析错误，不落入默认网络域。
2. **一次标准化**：解析器输出不可变的 `event_key = (epoch, sensor, source, file_id, record_offset/sequence, revision)`、规范化正文哈希、源记录哈希、`observed_at`、`accepted_at`、作用域、协议及类型化查询字段。相同来源位点同版本不同内容为**冲突**，停该来源并保留原文，哈希只是快速定位，必要时仍比对规范化正文；不同位点但相同服务公告是两次真实观测，不可按哈希删除。更正/撤销以业务键和版本表达，不能伪装为新设备。
3. **一个可恢复暂存**：能固定身份并保留到所有支路确认的 Zeek 原日志文件，直接作为顺序日志；轮转后由系统持有该文件，避免再复制一份正文。段清单固定解析器版本、标准化规则版本和预期内容哈希；重放必须使用相同版本，版本无法保持时先把未确认记录固化成规范化段，不能用新解析器悄悄改写同一事件。不能保证原文件留存的来源和直接被动抓包，也使用追加式规范化分段日志，完成文件及目录持久化后确认来源位点。段头含首尾位点、数量、哈希和 `epoch`。现有发现 spool 是基础，但需改成有界段与独立确认位点，不能靠无界小 JSON 文件堆积。若原日志与暂存必须共享慢盘，先核对额外读写成本再决定是否需要独立 SSD；[Elastic Filebeat 磁盘队列文档](https://www.elastic.co/docs/reference/beats/filebeat/configuring-internal-queue)也明确持久性需要额外磁盘读写。
4. **独立消费支路**：归档支路读取所有已启用协议事件；窄检索索引与设备投影分别维护 `archive_ack`、`search_ack`、`projection_ack`、失败和最老未确认位点。投影只读取明确准入的发现、身份或风险事件；某事件没有投影消费者时在段清单中明确标记“不适用”。支路互不等待，但必要的每条确认未完成前不能释放其原日志/暂存。ClickHouse 暂停时设备状态仍可更新，案件证据必须等归档核验；PostgreSQL 暂停时归档继续且投影缺口保持可重放。页面须显示相应新鲜度和证据待归档状态。[Zeek 官方集群架构](https://docs.zeek.org/en/current/frameworks/cluster.html)同样把流量解析的 worker 与日志汇聚的 logger 分开，避免采集解析承担下游存储负担。

使用本地持久分段日志而非先加 Redis/Kafka，是**本阶段的明确选择**：已有单机文件来源和 spool，可以较少组件实现按来源有序、独立确认和故障重放；Redis 缓存不是持久恢复边界。将来跨节点、多采集器或高可用要求出现时，再以持续输入、故障注入、磁盘容量和运维成本证明是否换为持久队列。Security Onion 的 [Zeek/Suricata→Logstash→Redis→搜索节点链路](https://docs.securityonion.net/en/3/main/ingest/)说明队列用于解耦和缓冲，并不说明后端可以长期低于输入吞吐；它也将高负载传感器与搜索资源分开部署，见[硬件说明](https://docs.securityonion.net/en/3/dev/hardware/)。

| 备选做法 | 本次结论 | 原因 |
|---|---|---|
| 所有原始协议记录、任务和当前状态都放 PostgreSQL | 不采用 | 大量逐事件回执、JSON、WAL 和索引与设备状态事务争用；只把有业务语义的选中事实放入 PostgreSQL |
| 全部改存 ClickHouse，直接用它算设备当前态 | 不采用 | 事件检索和聚合适合它；更正、撤销、来源冲突、案件事务及严格当前态需要可控的单库事务与键约束 |
| Redis 承担设备权威状态或以缓存消除积压 | 不采用 | 缓存不增加后端持续写入能力，也不能独立承担证据、冲突和案件保护；将来仅可对已验收的读模型作可失效缓存 |
| 本地可恢复日志 + CH 批量正文 + PG 选中事实 | 采用 | 对应当前单机来源与两类读取，删除热路径逐事件远端存在性检查，并保留独立恢复与明确水位 |

## 二、ClickHouse：唯一正文、批量写入和可预测检索

新代次的事件正文按保留契约**互斥路由**到普通流量短期归档或设备/路由器必要证据长期归档；同一事件不同时写入两张全文表。案件成立时向 PostgreSQL 复制的受保护证据是明确的法律/业务保留例外，不是第二份常规历史。可能进入案件的必要证据应在写入时确定保留类别，或者在普通流量 TTL 到期前完成案件保护；过期后不能声称仍能从引用恢复原文。正文包含完整标准事件及必要的源日志原文或可验证源引用；若源原文未保存，只能称“标准事件原文”，不能称“原始 Zeek 行”。留存期限以首次成功入库时间计算：设备相关热查 30 天、必要证据归档一年；普通流量按各自既定 TTL，不因发现证据自动延长。当前 `normalized_events` 7 天 TTL 和 `discovery_evidence_archive` 一年 TTL 的差异，不能靠改一个 TTL 解决。

| 目标数据集 | 最小字段及排序/分区意图 | 写入与读取职责 |
|---|---|---|
| `event_body_short` / `event_body_evidence` | `archive_month` 在首次归档尝试前持久确定并作为重试稳定的月分区键；`scope_id,event_key,content_hash,first_archived_at,accepted_at,observed_at,body`，按作用域和事件键排序以支持精确取证 | 互斥的唯一权威全文；直接批量插入，不在前面做 event ID 查重；TTL 依据成功归档时生成的 `first_archived_at`，不依据可能早很多的文件接收时间 |
| `event_search` | `scope_id,protocol,observed_at,event_key,body_ref` 加必要 IP/MAC/域名/端口标量；按实际“协议+时间”查询排序，其他高频键经查询计划核实后再建窄索引 | 有界日志列表、时间线和聚合入口；无 `payload_json/observer_json/flow_json` 完整副本 |
| 协议/风险特征 | 明确读取方需要的标量、窗口聚合及 `body_ref`，按其筛选键排序 | 批量写入或经过核验的轻量物化；不在物化视图中重复存全文或反复从 JSON 解析可提前类型化的字段 |
| 批次/段清单 | `epoch, source, segment_id, row_count, content_hash, archive_status, search_status` | 跨进程恢复和异常结果核对；平常不按事件逐条查 ClickHouse |

`body_ref` 包含保留类别、稳定归档月、作用域、事件键与哈希，使精确证据查询能限定分区和主键；查询不能只带 event ID 扫所有月。首次归档尝试跨月后重试仍使用原 `archive_month`，因此 ClickHouse 去重不因改分区而失效；`first_archived_at` 在真正插入时由服务端生成，保留期不被暂存等待缩短。ClickHouse `ORDER BY` 应按真实 `WHERE`/时间线选择，窄索引的额外写入量必须可测；官方说明排序键影响跳过 granule 的能力，且[按天过细分区可增加 part 压力](https://clickhouse.com/resources/engineering/clickhouse-optimize-table-final)。具体字段类型、分区和排序以目标版本、真实查询样本及 `EXPLAIN` 固定，不能直接改写现有已应用迁移。

归档写入器按可配置的**行数、字节、最长等待时间**三重条件合批；高吞吐优先足够大的同步批次，低流量可用经版本验证的 `async_insert=1,wait_for_async_insert=1` 服务端合批。最长等待时间纳入 5 秒时效预算，不能为凑大批而延后实时事件。每个段的排序、内容、目标分区和每张目标表的 `insert_deduplication_token` 固定，成功响应后记录批量确认。窄检索写入有独立确认；如未成功，可从仍保留的段或已确认的权威正文修复。**超时或断连不是失败确认**：先用段清单的事件键与目标表的归档月/作用域做异常路径的限定核对，完整则补记确认，缺失则重放同一不可变段；不能每个正常批次都先查再查，也不能盲目用新 token 重发。ClickHouse 的去重窗口有限，`MergeTree` 不是全局唯一约束；超过窗口的未知结果必须停在恢复核对，不能承诺“任意长期重放也绝无物理重复”。[ClickHouse 重试去重文档](https://github.com/ClickHouse/clickhouse-docs/blob/main/docs/guides/developer/deduplicating-inserts-on-retries.md)明确了窗口和 token 语义。逻辑查询对少量异常重复仍按稳定事件键防御；不在常规请求上使用 `FINAL` 或全表去重。

新流不与 `normalized_events`、`discovery_evidence_archive` 同时双写全文。先发布“能读旧表与新表、只写旧表”的兼容版本，再发布“按新 `epoch` 只写新表”的版本；旧版继续读取旧代次，兼容版可作为应用回退点。旧表只按现有保留期自然退出，任何提前退役都须先证明案件引用、查询、归档覆盖。这样迁移期也不人为制造新的重复全文。

## 三、PostgreSQL：仅存有界业务状态

PostgreSQL 接收的是**已选出的投影命令**，不是所有 Zeek 日志全文。归档确认无需在每个设备事务内远程查询 ClickHouse。选中事件的紧凑回执保存事件键、正文哈希、首次接收时间、应用结果和必要归档引用；按稳定首次接收月分区，保留窗口须覆盖最大可重放期，长期证据的窄定位清单仍留在归档。若一个事件是同内容重报，回执仍明确存在，但业务事实只更新末次观测/次数/有效期，不追加整份变化文档。

每个投影片段先在内存按 `(scope,device_key,source,fact_key)` 分组；组内保留确定的版本/来源顺序，只合并语义相同的重复观测，更正→撤销等不同转换即使同批也逐步保留审计结果。再以集合式写入把候选放到事务内暂存，**先插入回执，只有冲突键核对旧哈希**；不按条执行“查回执→查事实→UPSERT”。随后只锁受影响设备，按固定键序读取受影响的当前事实和分类候选；真实更正、撤销、晚到、自然过期与来源冲突各有独立状态转换。相同事实的最新观测时间更新可以发生，但若可见结论未变就不改整份设备状态或结果版本。必要变化历史存变化原因、前后值/哈希、事件引用和最小快照；完整原文留在 ClickHouse。事务同时提交回执、事实、当前态、变化和投影位点；租约代次防止过期消费者提交。PostgreSQL 的 `INSERT ... ON CONFLICT` 提供该单库原子更新，但[分区唯一约束必须包含分区键](https://www.postgresql.org/docs/current/ddl-partitioning.html)，因此重试必须使用首次接收月这一稳定分区键，不能用每次重试时间重新路由。

当前态拆成小型 `device_state` 行、按事实键的 `device_fact` 行、按字段/候选来源的有界分类候选及独立变化表；常用筛选和排序用结构化索引，不把大 JSON 作为列表和关联键。一个设备有上千条旧事实时，普通新公告的成本仍应由本次受影响键决定；极值失效只查询该字段下一候选。风险评分读标准化事实与有界窗口，写带证据引用、分数、置信度、窗口和解释的决策。案件、策略命中及“仅记录、未执行”的动作/上报各保留自身状态，但不嵌入整批原始日志；案件创建在同一 PostgreSQL 事务中从已核验归档取回并保护必需证据，哈希不符或归档未就绪则拒绝引用。

## 四、从页面/API 倒推读取路径

| 用户要查什么 | 唯一主要读取方 | 查询边界及失败语义 |
|---|---|---|
| 当前设备/路由器列表、分类、当前地址 | PostgreSQL 小型状态与结构化检索关系 | 作用域、类型、状态、游标和页大小在 SQL 完成；不扫历史、不跨 ClickHouse Join；返回投影水位和处理中/过期状态 |
| 单设备详情 | PostgreSQL 当前事实与候选 | 首包只给当前结论；历史地址、服务、变化独立分页；区分当前、最后观测、历史和低置信候选 |
| 一条证据/案件证据 | 稳定引用→ClickHouse 权威正文；案件保护副本从 PostgreSQL 读 | 限入库月/作用域/事件键，核对哈希；归档待确认不能报“无证据”；案件正文独立于常规 TTL |
| 协议日志、时间线、DPI 搜索 | ClickHouse 类型化窄检索表，按需回查正文 | 必须有作用域、时间范围与页大小；不在 PostgreSQL 做全量事件列表，也不返回整页大 JSON |
| 风险结果、策略记录、统计 | PostgreSQL 决策/动作当前态；ClickHouse 预聚合或独立统计任务 | 实时决策不依赖页面全量聚合；复杂统计有版本、水位和独立预算，失败不伪装为零 |

相关标准事件**首次成功入库**到 API 正确反映处理结果的逐条 5 秒要求不改变：分别记录来源接收、持久日志落盘、首个数据库成功入库、PG 投影提交、ClickHouse 归档确认和 API 首次可见时间；起点取该事件在 PostgreSQL 回执/投影或 ClickHouse 权威归档中更早的成功提交时间，不能重试时重置，另报告采集到可见的总延迟以免暂存排队被排除在外。PostgreSQL 热历史保留期限也不得早于这个起点加 30 天。归档与投影并行时若 PG 先提交，状态已可见而原文仍在归档中，接口须明确“证据待归档”，案件引用继续拒绝。若 ClickHouse 先提交，PG 查询延迟仍计入 5 秒。设备状态 API 继续验收 P95≤500 毫秒、P99≤1 秒；失败与超限逐条记录。缓存仅按结果版本失效，不能用旧缓存充当新结果。详见[设备中心查询契约](device-center-storage-query-design.md)。

## 五、一致性、积压和故障处理

| 故障点 | 必须发生的事 | 禁止发生的事 |
|---|---|---|
| 采集进程在分段日志确认前退出 | 来源位点不推进，按同一来源位点重新读取 | 丢失输入却显示来源已追平 |
| ClickHouse 成功但响应丢失 | 保留段，按段/哈希限定核对后补确认或同 token 恢复 | 每次正常写前扫 event ID；未知结果用新 token 盲重试 |
| PostgreSQL 投影提交前退出/租约丢失 | 保留投影位点缺口；回执和状态同事务重放，过期租约不得提交 | 把已归档当作已投影，或让旧线程覆盖新事实 |
| PostgreSQL 已投影但归档未核验 | 状态可带待归档标记，段仍保留，案件不能保护缺失原文 | 把待归档标成可取证，或清理唯一暂存 |
| 单事件内容冲突、坏记录 | 隔离该来源/事件并给出具体位点、哈希及操作结果；其他独立来源可继续 | 静默丢弃、标成功、把冲突合并成同内容重报 |
| 磁盘满、队列上限、网络采集不可背压 | 按来源停止扩量并显式记录丢包/缺口，保持已写入段 | 宣称“无积压”或用覆盖旧日志掩盖丢失 |

积压必须分开看：来源文件未读字节、持久日志未归档段、未投影选中事件、ClickHouse 异步缓冲/parts、PostgreSQL 回执与设备状态延迟。对每条支路记录输入率 `λ`、完成率 `μ`、最老年龄、失败率和队列字节。持续稳定必须证明队列有界且没有长期正增长，突发后能在限定时间内回到边界内；当队列已接近零时，轮询和两秒小批合并造成的数 KB 端点波动不能单独判作容量不足。队列容量按实际峰值和要求可承受的中断时间设计，不能仅按当前平均速率。持续背压时先停新增协议并报告硬件/成本缺口，不靠放宽超时、提高并发或跳任务宣称达标。

**184 单机硬件是独立发布门槛。** 先只读核对当前 PostgreSQL、ClickHouse、日志/spool 是否竞争同一磁盘及其 IOPS、iowait、WAL、CH part/merge、冷热查询；此前记录的机械盘现象只能作为调查线索。若共用慢盘在目标输入率下已饱和，需把持久日志与 PostgreSQL WAL/索引、ClickHouse 热数据至少迁到足够的 SSD/NVMe 或分开节点/盘，按真实负载确认；这不是 PostgreSQL 不适合设备状态，而是高频逐事件随机读写与 ClickHouse 合并争用同一介质的架构上限。Security Onion 也将热搜索层部署于 SSD/NVMe，并区分 sensor/search 资源，见[存储说明](https://docs.securityonion.net/en/3/dev/elasticsearch/)。

## 六、新鲜起点、切换与验收顺序

1. 冻结当前读取方清单、184 真实版本、表与队列水位、每协议输入率/平均及峰值字节、磁盘和延迟基线；把尚未处理的旧任务、文件段和时间范围列入**取消/丢弃清单**，不改写为完成。为每来源记录新 `epoch` 的文件身份与起始位点；旧状态与新状态通过 `epoch` 隔离，旧未验证结论不直接作为新当前态。旧证据按现有期限保留或经授权的清理程序退役，不回填。
2. 先完成兼容读取和新表/分段日志迁移，再切新来源到新写入器；不得修改已应用迁移。新代次只写一套正文。通过故障注入证明文件截断/轮转、段半写、CH 超时但成功、CH 部分写、PG 提交但确认丢失、跨月重试、租约丢失、重复/乱序/撤销、案件保护和冲突处理。对每个真实读取方做新旧结果影子核对，不能凭 `readyz` 替代功能验收。
3. 受限的真实新发现输入先验收：逐条记录 5 秒可见性，至少两个完整连续 15 分钟窗口内证明来源未读、归档待确认和投影待确认均有界，无持续增长，突发后可恢复；同时报告每窗输入和消费字节、最老年龄、超时、冲突、CH parts/merges、PG WAL/锁/IO、状态 API P95/P99。184 当前 DHCP 绑定来源的本轮预置边界为每窗未读 P95≤8 KiB、峰值≤16 KiB、连续 30 分钟末尾 5 分钟的未读中位数不高于开头 5 分钟超过 4 KiB，归档待确认最老年龄<30 秒，且不得有 60 秒无进度。用户于 2026-10-25 明确允许按有界积压取代“每个窗口末端字节必须净下降”；边界须在窗口结束前固定，不可事后按结果改阈值。任何不可解释的逐条超限、持续增长、内容冲突或资源保护触发都停止新增输入，保留证据和任务；不用造数或回填掩盖。
4. 身份、路由器和风险投影按同一模型迁移并证明各自业务语义；逐张收敛旧协议/风险全文表，每张先列读取方、留存期和案件引用，完成影子比较与归档覆盖后退役。每一步提供每事件 SQL 次数、每 MB 标准事件产生的 CH/PG 字节、单位事件 WAL/CPU/IO、净消化速率、段恢复耗时和查询延迟。
5. 只有这些依赖通过后，按[Zeek 扩协议计划](zeek-protocol-expansion-plan-184-20261024.md)单协议开放，并分别证明归档、投影、检索和业务结论。普通 `conn`/DNS/HTTP/SSL 等高流量日志是否启用由测得的 `λ`、硬件与保留容量决定，不以“Zeek 已产生日志”代替端到端通过。

该设计符合现行 [AGENTS.md](../AGENTS.md) 的 PostgreSQL 结果库、ClickHouse 事件/归档、增量更新、5 秒可查询与新组件收益评估要求；不需要通过放宽这些约束来掩盖问题。实现前须验证目标 ClickHouse 版本的插入去重/物化视图行为，以及本地分段日志的断电恢复和磁盘容量。本文的确定性是**数据职责、提交协议和查询路径**；在 184 的实际吞吐上限仍须测量，不能提前承诺。
